# Discover `system-prompt.md`; keep `name`, reject `greeting.txt`

`1-filesystem-derived-tools.md` established that a file beside `agent.ts` can BE
the thing, named by its own path, registered by nobody. This applies the same
rule to the one remaining field of an agent that is a DOCUMENT rather than a
value — the system prompt — and argues against applying it to the two fields it
would be natural to sweep up with it.

The example that prompted this is `night-owl/agent.ts`, which after tool
discovery is four fields:

```ts no-check
export default agent({
  name: "Night Owl",
  systemPrompt:
    "You are Night Owl, a cozy evening companion. …\n\nUse run_code for sleep calculations:\n- Each sleep cycle is 90 minutes, plus 15 minutes to fall asleep\n- Bedtime = wake_time - (cycles * 90 + 15) minutes\n…",
  greeting: "Hey there, night owl. …",
  builtinTools: ["run_code"],
});
```

That `systemPrompt` **is markdown** — a paragraph, a heading-shaped line, and a
four-item bulleted list — spelled as `\n\n` and `\n-` escapes inside a
single-line string literal. It has no wrapping, no preview, and it diffs as one
line no matter which bullet changed. Twelve of this repo's twenty-two templates
already keep that document in a file; ten do not, and nothing decides which.

**No numeric-prefix dependency, and `1.5` is a claim about lineage rather than
ordering.** It consumes `1-filesystem-derived-tools.md`'s discovery rule and
`tools-off-the-agent-def.md`'s generated-entry seam, and nothing consumes it. It
should land AFTER those two, because it should not invent a second discovery
mechanism beside the one they are still settling.

## Outcome: landed as designed, and the first open question dissolved

Every scope row is done. `system-prompt.md` beside `agent.ts` IS the system
prompt; fourteen templates keep one and none imports it; `night-owl/agent.ts` is
three fields, which is what this document predicted. `greeting` is still a field,
`name` is still a field, and there is no new konsistent convention.

**The "ask rollup's AST" question is retired rather than answered, and the
mechanism that retired it is better than either option the question offered.**
`withSystemPrompt` compares VALUES: the def's resolved prompt is either the
framework default (the author declared none → the file becomes it), or it
CONTAINS the file's text (imported, verbatim or composed → left as built), or it
is neither (a file nothing reads → error). Two reasons that beats the AST:

- **The entry is generated BEFORE the build**, so at the moment the decision has
  to be encoded there is no module graph to ask. The precedent added to the
  question above is real — eve does query `parseAst` for this class of
  question — but eve asks it from a gate and from an editor, both of which run
  over source as a separate pass, not from inside the entry generator.
- **An AST answers a weaker question.** It can see that `system-prompt.md` was
  IMPORTED; it cannot see whether that value reached `systemPrompt`. An import
  bound to an unused local is precisely the bug, and it would pass. The resolved
  prompt cannot be fooled that way, and composition needs no special case.

So the row that said "the bundler knows its own module graph" was pointing at the
wrong seam, exactly as `1-filesystem-derived-tools.md`'s entry-generator
assumption was — the third time in this lineage that the mechanism needed
correcting while the diagnosis held.

**The watcher answer is confirmed independently** (`isIgnoredPath` filters by
path SEGMENT, excluding only `node_modules` and dot-entries, and every chokidar
`all` event drives a full rebuild-and-swap), and the cost note stands as written:
a prose-only edit currently pays a bundle rebuild plus a server swap, and if that
becomes the complaint the fix is a structural-vs-runtime fingerprint split rather
than a narrower watch glob.

**The starter-eval question is answered: nothing reads it.** No `expectations.mjs`
check, no template spec and no `templates.test.ts` assertion reads a
`systemPrompt` literal out of source — the only mention anywhere is a comment.

**No epoch bump was needed.** `systemPrompt`'s type did not move, and
`withSystemPrompt` lives on `@alexkroman1/aai/manifest`, which is not part of the
contracted authoring surface (a build performs the attachment; an author never
writes it).

Two things worth keeping that the plan did not anticipate:

- **`_tool-discovery.ts` is `_discovery.ts`** now, because it resolves both halves
  of what the filesystem declares. `templates.test.ts` validates every template's
  prompt file through it, so an empty or orphaned one fails for all of them at
  once.
- **That gate needed a non-vacuity guard, and the first one did not work.**
  `withTemplatePrompt` no-ops for a template with no file, so a glob that
  stopped resolving would make every template look like that case. The first
  guard derived "which templates have a file" from the same glob it was
  checking, and was verified by A/B NOT to bite. It reads the filesystem
  instead — two independent sources is the only shape that catches a dead glob.

## The measurement

| shape | templates | count |
| --- | --- | --- |
| `system-prompt.md` + `import … from "./system-prompt.md?raw"` | code-interpreter, dispatch-center, health-assistant, infocom-adventure, math-buddy, personal-finance, pizza-ordering, plan-and-execute, retail, solo-rpg, support-line, travel-concierge | 12 |
| inline string literal in `agent()` | embedded-assets, night-owl, web-researcher | 3 |
| composed in `agent.ts` (array join, or file + computed suffix) | recap-workflow, research-workflow, pizza-ordering | 3 |
| no `systemPrompt` (framework default) | link-digest, pipeline-simple, redline, simple, transcription-workflow | 5 |

So the file convention is already the MAJORITY, already documented in
`scaffold/CLAUDE.md` ("`system-prompt.md` — Long system prompts (optional,
imported)"), and already carried in the shipped guide's example. What it is not
is DERIVED: every one of the twelve spells the same import line, and the ten
without a file are not wrong about anything, because nothing says a prompt lives
in a file.

Two things that import line costs, beyond being written twelve times. It is a
**Vite-ism** (`?raw`) in user-authored space — the same objection
`1-filesystem-derived-tools.md` raised against `import.meta.glob`, and survivable
now only because `tools-off-the-agent-def.md` put a bundler in front of
self-hosting. And it is the only reason `packages/aai-templates/templates/**/
system-prompt.md` needs its markdownlint exemption to be about templates rather
than about a convention the SDK owns.

## Prior art: eve authors neither a name nor an instructions string

`~/Code/eve`'s `defineAgent` has no `name` and no `instructions` field. A whole
agent definition there is:

```ts no-check
export default defineAgent({ model: "anthropic/claude-opus-4.6" });
```

with `instructions.md` sitting beside it. Three parts of how it does this are
worth taking, and one is worth deliberately not taking.

**The prose slot has three forms, and the middle one is the escape hatch.**
`discoverInstructionsSource` (`packages/eve/src/discover/grammar.ts:181`) accepts
`instructions.md`, `instructions.{ts,cts,mts,js,cjs,mjs}` — a MODULE, for prose
that has to be computed — or an `instructions/` DIRECTORY of several files. A flat
file and a directory may coexist, with the flat file first. That is the answer to
this repo's composed prompts without a special case: a computed prompt is a
module rather than a string on the definition.

**The slot is REQUIRED**, and its absence is a diagnostic naming every accepted
filename (`DISCOVER_REQUIRED_INSTRUCTIONS_MISSING`). Ours cannot be required —
five templates deliberately run on `DEFAULT_SYSTEM_PROMPT` — but the shape of the
error message is the model to copy.

**A rename carries a deprecation warning.** eve still loads a legacy
`system.md` and warns, which this repo does not need
(`research/README.md`: no shims) but which shows the slot name is a published
contract once discovery exists. Pick `system-prompt.md` and mean it — twelve
templates and the shipped guide already say it.

**What NOT to copy:** eve sorts directory entries with `localeCompare`
(`grammar.ts:174`). For CONCATENATED prose the order is semantic, and this repo
already has the rule from the api-report work — sort by code unit, never
`localeCompare`, which answers to the runtime's ICU default and makes the same
tree produce different output on a different machine.

## `name` stays, and the reason is not sentiment

The direct answer to "how does eve name the agent": **it derives an ID and has no
display name at all.** `deriveAgentIdFromRoots(appRoot, agentRoot, packageName)`
(`packages/eve/src/discover/manifest.ts:350`) returns `packageName ??
basename(appRoot)` for an agent at the root or at `agent/`, and the relative path
otherwise; a subagent's name is its directory (`subagents/echo-marker` →
`"echo-marker"`), which is principle 7 applied exactly as written. The only
human-facing string on `defineAgent` is `description`, and that exists for the
MODEL — it is the hint a parent agent uses to decide to delegate.

Our `name` is a different thing wearing the same word. It is display prose: it
is what `GET /client-config` serves (`sdk/client-config.ts:68`) and what the
default client prints in the shell, and it is the ONE required field on
`AgentDef` — `systemPrompt`, `greeting`, `maxSteps` and `tools` all have defaults
and `name` does not, which `agent()`'s own doc comment calls out.

Deriving it means title-casing a directory name, and that is wrong the moment an
acronym appears: `night-owl` → "Night Owl" works, `solo-rpg` → "Solo Rpg" does
not, and neither does any product name with internal capitalization. It is also
the wrong SOURCE — the project directory is a developer's choice and the deployed
slug is generated by the platform ("a slugless deploy is named `human-id` words
plus a random suffix"), so neither is a name anyone chose to show a caller.

eve avoids all of this by not rendering an agent name anywhere. We render one. So
principle 7 does not reach `name`, and the honest reading is that eve's `agentId`
has no counterpart in our surface at all — the slug is it.

## `greeting.txt` is REJECTED

It is the natural next sweep and it is a worse idea than it looks:

- **It is one sentence, not a document.** Every greeting in the tree is a single
  line. The whole argument above is that a system prompt is markdown written as
  escapes; a greeting has no structure to lose.
- **One of them is INTERPOLATED.** `support-line` opens with
  `` `${PRODUCT} support, you're …` ``, which a `.txt` file cannot express. Under
  eve's own grammar the answer would be `greeting.ts`, i.e. a module whose entire
  content is one template literal — a file, an import and a default export to
  replace a field.
- **Five templates omit it** and take `DEFAULT_GREETING`, so the file would be
  absent as often as present, and its absence means two different things
  (deliberate default, or forgotten).
- **It is client-facing DATA, not authored prose.** It crosses the wire in
  `client-config` beside `name` and `page`. Those three travel together and
  should be declared together.
- **It starts a slope with no natural stop.** `greeting.txt` invites `name.txt`
  and `max-steps.txt`; the line that holds is **a document goes in a file, a
  value stays in the call**, and `greeting` is a value.

Same verdict, same reason, for `sttPrompt`: it is a vocabulary hint, not prose.

## Design

`system-prompt.md` beside `agent.ts` is discovered and becomes the agent's
`systemPrompt`, through the mechanism `tools-off-the-agent-def.md` already
builds: the generated entry reads the project directory at build time and lowers
what it finds into static imports, so nothing scans a filesystem at run time and
nothing carries a Vite-ism into user space.

- **`agent({ systemPrompt })` stays.** Three templates compose their prompt
  (`recap-workflow` and `research-workflow` join an array; `pizza-ordering` appends
  `menuText()`), and a computed prompt is legitimate for the same reason an
  inline tool is. This is a default, not a replacement.
- **Declaring both, with the file unreferenced, is a BUILD ERROR.** The failure
  this must prevent is "I edited `system-prompt.md` and nothing changed", which
  is the silent-absence failure `1-filesystem-derived-tools.md` opens with,
  pointing the other way. Composition therefore stays EXPLICIT: `pizza-ordering`
  keeps its `?raw` import and its computed field, and the error fires only when
  the file exists, no `systemPrompt` reads it, and one is declared anyway.
- **The precedence chain has a third link, and it is doc 6's.**
  `6-dynamic-agent-definition.md` makes `systemPrompt` resolvable per session, so
  the order is discovered file → explicit field → resolver. Worth noting that
  this is the field where a resolver is SAFE: doc 6's new constraint is that a
  resolver may not decide anything `/client-config` answers with, and
  `client-config` serves `name`, `greeting` and `page` — not the system prompt.
  The same fact that rejects `greeting.txt` is what makes `systemPrompt` the
  right first resolver field.
- **An empty or whitespace-only file is an error naming the file**, not a silent
  fall-through to `DEFAULT_SYSTEM_PROMPT`.
- **A nested `system-prompt/` directory is out of the first cut** — eve supports
  one and no template here needs one, so picking a concatenation order now would
  freeze a guess. Reject it with a message rather than inventing a convention,
  the same call `1-filesystem-derived-tools.md` made about nested tool files.

### No konsistent convention, for the reason the last one was retired

`template-tools` was retired because discovery made the export name
unobservable, leaving nothing per-file to assert. Here the file's NAME becomes
load-bearing, which looks like something to check — and is not, because the
checks are build errors in the discovery step (unreferenced file, empty file,
nested directory), each naming the file. A convention would be a second
enforcement of a rule the build already refuses to violate, and the gate's own
failure mode is that a convention matching nothing prints the same
"No violations found" as a healthy run.

## What it buys, in the terms this repo measures

- **Prompt iteration is the main loop of agent authoring**, and it is currently
  the one edit that lands in the least reviewable place: a string literal with
  escaped newlines diffs as a single line. Ten templates, plus every project the
  studio generates, are in that shape today.
- **The studio's coding agent edits prompts constantly.** A prompt in its own
  file is a smaller, more targeted write than a re-emission of `agent()`, and a
  failed edit cannot take the tool map or the mode with it.
- **`agent.ts` becomes what tool discovery started making it**: a declaration of
  what the agent IS — name, mode, builtins, providers — with the prose and the
  behaviour both in files. `night-owl/agent.ts` ends at three fields.

## Open questions

- **Can the generator tell whether the file is REFERENCED?** The
  both-is-an-error rule needs to distinguish `pizza-ordering` (imports the file,
  composes it) from a mistake (file present, ignored). The bundler knows its own
  module graph, so this should be a question to rollup rather than a scrape of
  source text — confirm that before committing, because a source scrape is the
  fragile half of every version of this idea. Fallback: make composition
  explicit some other way, never a warning.

  Precedent that this is the right instinct: eve asks rolldown's `parseAst` for
  exactly this class of question in TWO places — a gate that walks the shipped
  `bin/` files and fails any bare import that is not a declared runtime
  dependency (`scripts/check-bin-runtime-dependencies.mjs`), and the
  `source-change/` editors that locate `defineAgent({ … })` in an author's file
  and splice one property. So "ask the bundler's AST about authored source" is an
  established mechanism over there rather than a hope.
- **Does the studio's starter-eval grade prompt text out of source?**
  `expectations.mjs`'s "prompt" is the STARTER prompt, not the agent's — but
  `checkMode(config, source)` and `checkUi` do read generated source, so confirm
  none of them asserts on a `systemPrompt` literal before moving it into a file.
- ~~**Does `aai dev`'s watcher rebuild on a prompt-file edit?**~~ **Answered:
  yes.** `watchDirectory` takes chokidar's `all` event and every event drives a
  full rebuild-and-swap, and `isIgnoredPath` filters by path segment rather than
  by extension — so a `.md` edit restarts exactly like a `.ts` one. See the same
  question, now closed, in `tools-off-the-agent-def.md`. What remains is a COST
  question rather than a correctness one: a prompt is edited far more often than
  a tool is added, and every edit currently pays a bundle rebuild plus a server
  swap. If that becomes the complaint, the fix is eve's structural-vs-runtime
  fingerprint split, not a narrower watch glob — a prose-only change is the
  clearest possible example of a non-structural one.
- **Should the five default-prompt templates get a file too?** Making the slot
  required is eve's choice and would remove "absent means two things" — but
  `DEFAULT_SYSTEM_PROMPT` exists precisely so a five-line agent can exist, which
  is what `simple` and `pipeline-simple` are for.
