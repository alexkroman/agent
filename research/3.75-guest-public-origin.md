# Carry the agent's public origin into the guest

Read against eve's Vercel adapter (`~/Code/eve`, `packages/eve/src/internal/nitro/`
plus `src/public/next/`), which is the most developed example available of a voice
/ agent framework adapting itself to somebody else's hosting scheme. Of the nine
mechanisms it carries, **one transfers**, and it closes a gap this repo already
names in prose. The other eight are either answered more strongly here, or
unrepresentable here, and the reasons are worth recording because "adopt eve's
adapter model" is a question that will be asked again.

## Sequence: land it beside 3, and before 4

**This plan depends on nothing and nothing depends on it.** There is no mechanism
here that another doc consumes and none it needs built first, so the prefix is
recording the second thing `research/README.md` allows a number to mean — two
adjacent numbers that are "independent and parallelizable", stated in the doc's
own text, which this is that statement. It is `3.75` rather than an integer
because both facts about its position are relative to plans that already have
numbers:

- **It must not queue behind `3-session-event-stream.md`.** Doc 3 changes the
  protocol union, the reconnect path and adds a subscriber surface; this touches
  `warm-harness.ts`'s boot env, one `createServer` option, and one accessor on
  `ctx.workflows`. **Zero files in common**, so it is reviewable and landable
  while 3 is in flight — and it should be, because it is the only entry in this
  directory that is a live correctness bug rather than a refactor or a new tier.
  The platform half is already shipped and answering; it is the guest half that
  hands out a URL naming a container that will not exist.
- **It must precede `4-callback-surface-collapse.md`**, weakly but really. Doc 4
  is a per-file audit of the `on*` option surface with a count ratchet; adding
  `publicUrl` to a server option bag afterwards means adding a field to a bag
  that has just been frozen against growth. One field is cheaper to carry
  through an audit than to append to a finished one.

It is likewise parallelizable with `3.5-store-backend-fidelity.md` — the `3.75`
only means "after that number", not "because of it".

## What eve's adapter actually is

There is no adapter module. eve compiles to **Nitro**, and Nitro's `vercel`
preset emits the Vercel Build Output API v3 tree. eve's Vercel-specific code is:

1. **One host decision as a string** — `process.env.VERCEL ? "vercel" : undefined`,
   read at three sites, threading a `preset` through the build and additionally
   selecting the workflow world and whether local sandbox backends are pruned.
2. **A preset options object** (`vercel-build-output-config.ts`, 60 lines):
   `config.version: 3`, `config.framework: { slug: "eve", version }`, and one
   `functionRules` entry that makes a second, queue-triggered function
   (`/.well-known/workflow/v1/flow`) fall out of the same bundle.
3. **An unguessable per-build cron path** — the default Vercel cron path is
   public and leans on `CRON_SECRET`, so eve mints
   `${EVE_ROUTE_PREFIX}/cron/<32 random bytes>` per build and writes it into
   `nitro.options.vercel.cronHandlerRoute`, from which the preset both registers
   the handler and emits `config.crons[].path`.
4. **Four named post-build transforms** over `.vercel/output/` — re-materializing
   the flow function to keep traced symlinks relative, pruning non-eve `*.func`
   and repointing route symlinks at a shared `eve/__server.func`, prefixing
   `crons[].path`, copying host middleware.
5. **Services-based co-deployment** — `withEve()` writes `services` into
   `.vercel/output/config.json` so an agent is a `framework: "eve"` service
   behind the user's own Next app, plus the inverse read at agent-build time.
6. **`EVE_PUBLIC_ROUTE_PREFIX` baked into the flow function's environment**, "so
   callback-URL minting inside the deployed workflow runtime resolves a routable
   path when a multi-agent host proxies the agent behind a prefix."
7. **Platform project-settings sync** — `framework: "eve"` is a real Vercel
   Framework Preset, PATCHed through `vercel api`, and flipped back to `nextjs`
   when the project grows a host app.
8. **Build-time prerequisite validation that FAILS** — `runVercelBuildPrewarm`
   aborts before bundling when sandbox templates are needed and
   `VERCEL_OIDC_TOKEN` is absent, with "Do not deploy the generated
   .vercel/output" in the message.
9. **Runtime bindings** to Vercel primitives — Sandbox as a sandbox backend,
   OIDC for auth, and tracing via `globalThis[Symbol.for("@vercel/request-context")]`
   rather than an OTLP endpoint.

## Mechanism-by-mechanism

| eve mechanism | here today | verdict |
| --- | --- | --- |
| Host decision as one threaded string | `sandbox-backend.ts` — explicit `SANDBOX_BACKEND` wins, unknown values THROW, `isLocalDev` false whenever `SUPABASE_STORAGE_BUCKET` is set so production can never resolve the host-local backend, and no fallback at spawn | **answered better** — a silent fallback is the failure mode eve's `undefined` preset invites |
| Vendor build-output emission | the deploy artifact is `{ worker, clientFiles, env }` gzipped to `POST /deploy`; we ARE the host | **unrepresentable** — nothing to delegate to |
| Post-build normalizers over an output tree | the artifact is one ESM string; there is no tree to normalize | **unrepresentable, and that is a win** — the whole class of "the emitter wrote something we have to correct" is absent by construction |
| `framework: { slug, version }` provenance | the bundle ships its own runtime (`__aaiCreateRuntime`), so a deployed agent runs the SDK version in the author's lockfile; plus `GUEST_CONTRACT_VERSION` and a per-deploy `harness_image_tag` | **answered better** — eve gets version coherence by rebuilding everything per deploy; we get it without the rebuild |
| Unguessable trigger path ("the path is the secret") | the workflow webhook token, and `guest-readiness`/session broker tokens | **already held** |
| Route surface declaration | `GUEST_ROUTES` + `GUEST_ROUTE_EXPOSURE` (a missing entry is a compile error) + `guest-routes.test.ts` introspecting the real orchestrator + rule 12 reading both trees as text | **answered much better** — eve decides membership with `path.includes("/eve/v1")` |
| Platform project-settings sync | nothing to sync: "the platform stores no agent config", and even the broker's name/greeting are PROXIED from the guest's own `/client-config` | **unrepresentable, deliberately** — eve's 300-line `vercel-project-framework.ts` exists only because Vercel holds a Framework Preset that can disagree with the repo |
| Build-time prerequisite failure | `aai build` evaluates the bundle before writing it (so a worker whose top level throws is never left on disk as what `npm start` boots); `_preflight.ts` WARNS on missing credentials, correctly, because the CLI cannot see secrets already stored server-side | **already held, with the stance argued** |
| Co-deployment behind the user's own app | `server.mjs` self-hosting; a browser client pointed at a deployed slug | **declined — see below** |
| Public mount carried into the deployed runtime | **nothing** | **ADOPT** |

## The gap: a minted callback URL names the guest, not the agent

`packages/aai-server/CLAUDE.md` already states it, under "Durable workflows":

> **One gap this deliberately leaves open.** The URL the DevKit MINTS still names
> the guest's own origin — `getWorkflowMetadata().url` is
> `http://localhost:<port>` off the running process, and its only override is
> Vercel's, which also switches on a replay watchdog that calls
> `process.exit(1)` inside what is also a voice guest. So an author composes the
> durable URL from the hook's `token` plus their agent's public origin; this
> route is what answers it.

So the platform half is built — `workflow-webhook-handler.ts` brokers
`POST /:slug/.well-known/workflow/v1/webhook/:token` and boots a sandbox for a
run parked days ago — and the guest half hands the author a URL that resolves to
the inside of a container that will not exist when the payment provider calls
back. `createWebhook()` is the DevKit's only third-party waitpoint; no template
demonstrates it, which is a symptom rather than a coincidence.

### Why the obvious one-line fix is wrong

`configureWorkflowWorld` (`packages/aai/host/workflow-world.ts:107`) already sets
`WORKFLOW_LOCAL_BASE_URL` for the local world, with the comment "Loopback, not
the bind host: this URL is only ever dialled by this process." That comment is
right, and it is the reason pointing that variable at the public origin would be
a bug rather than a fix. Verified in the installed DevKit
(`@workflow/world-postgres/dist/queue.js`, `@workflow/world-local/dist/config.js`,
both also visible in `packages/aai-guest/dist/harness.mjs`):

- `resolveBaseUrl(config)` is documented as resolving "the base URL for **queue**
  requests", and its order is `config.baseUrl` → `WORKFLOW_LOCAL_BASE_URL` →
  `config.port` → `PORT` → an autodetect probe against
  `/.well-known/workflow/v1/flow?__health`.
- The world then calls `getLoopbackTarget(baseUrl)` and behaves differently when
  the base IS loopback.

That base is what the queue dials `flow` and `step` on — the two routes
`GUEST_ROUTE_EXPOSURE` declares `guest-internal` precisely because they are
unauthenticated *and* loopback is the whole gate. Repointing it at the platform
would (a) 404, since nothing routes those paths, and (b) if anyone ever "fixed"
the 404 by adding routes, hand any caller an unauthenticated way to replay
another tenant's run. **In production we set it to nothing at all** — the
Postgres world branch sets only `WORKFLOW_TARGET_WORLD` and
`WORKFLOW_POSTGRES_URL` — so the autodetect finds `http://localhost:<port>`,
which is correct for dispatch and is also what gets minted.

### What eve's shape actually is, and the DevKit's own version of it

eve does not override the base. It carries the public **mount** as a separate
value (`EVE_PUBLIC_ROUTE_PREFIX`), bakes it into the flow function's environment
through `functionRules`, and consumes it in its own URL construction —
independently prefixing `crons[].path` in the build output with the same value.
Two concepts, two variables, one source.

The DevKit has a first-class version of the second concept that neither repo is
using: `setWorkflowBasePath(basePath)` / `getWorkflowBasePath()`, stored on
`globalThis[Symbol.for("@workflow/core/basePath")]` and consumed by both
`createWorkflowBaseUrl(origin)` and `createWorkflowUrl(baseUrl, route)` in
`@workflow/utils/dist/workflow-routes.js`. Note it applies to **every** route,
`flow` and `step` included, so it is not a drop-in either: prefixing those would
have to be matched by the guest serving the prefixed paths.

## The proposal

**Deliver the agent's public base URL into the guest, and mint from it.**

1. **Boot env.** `warm-harness.ts`'s `agentBootEnv` (the one place both backends
   build the agent-mode exec env) gains `AAI_PUBLIC_BASE_URL` — the origin plus
   the slug, e.g. `https://<platform>/<slug>`. The broker already has both
   halves at spawn: `resolvePublicOrigin(req)` and the slug it is brokering.
   This is an ADDITIVE boot-env change, the same shape as `AAI_BUNDLE_URL`, so
   it needs a `GUEST_CONTRACT_VERSION` bump and nothing else — an older pinned
   harness ignores it and behaves as today.
2. **SDK option, not env sniffing.** `PassthroughServerOptions` (and therefore
   `createServer` / `createAgentServer`) gains `publicUrl?: string`. The guest
   passes `AAI_PUBLIC_BASE_URL`; `server.mjs` passes `process.env.PUBLIC_URL`;
   `aai dev` passes its own origin. Sniffing an `AAI_*` variable inside the SDK
   would make the SDK read the platform's vocabulary, which the
   harness↔bundle contract's "deliberately tiny" rule exists to prevent.
3. **One authored accessor.** The composition currently left to the author
   becomes `ctx.workflows.webhookUrl(token)` (name to be settled), returning
   `${publicUrl}/.well-known/workflow/v1/webhook/${encodeURIComponent(token)}` —
   the same path `WORKFLOW_WEBHOOK_PREFIX` and `webhookToken()` already own in
   `host/workflow-serve.ts`, so both ends derive it from one constant. With no
   `publicUrl` configured it THROWS naming the option, rather than returning a
   `localhost` URL that fails weeks later at a third party.
4. **`WORKFLOW_LOCAL_BASE_URL` is not touched.** Queue dispatch stays loopback,
   `flow`/`step` stay `guest-internal`, and rule 12 keeps holding.

### The caveat, stated because it is real

The value is baked at spawn, and there is **one sandbox per slug fleet-wide**, so
a platform reachable on more than one public origin would serve every session
from the origin whichever request happened to spawn the guest. That is already
the operator's lever — `AAI_PUBLIC_ORIGIN` "is the way to take the choice away
from callers", per `public-origin.ts` — and a deployment with two live origins
owes it. Worth one sentence in `aai-server/CLAUDE.md`; not worth a per-request
mechanism, because a URL handed to a payment provider has to outlive the request
that minted it anyway.

### The one thing an implementation must confirm first — ANSWERED

I traced the DevKit's route builders and its queue base-URL resolution, but not
the mint site for `createWebhook()`'s own `url` property — the bundled call site
did not fall out of a grep of `harness.mjs`. So the open question is whether
`createWebhook()` returns a URL the SDK can leave alone (in which case the
accessor above is the whole change and the hook's own `url` should be documented
as guest-local), or whether it must be intercepted. `aai-cli`'s
`dev-workflow.scenario.test.ts` is the tier that can answer it — it is the one
place a real world and a real HTTP delivery already run — and answering it is
step one, not a detail.

**It is the first branch: `createWebhook()` mints a `url`, it is guest-local, and
the SDK SUPPLEMENTS it rather than intercepting it.** The mint site is one
line —
`@workflow/core/dist/workflow/create-hook.js`, `hook.url = createWorkflowUrl(url,
{ type: 'webhook', token: hook.token })`, where `url` is `getWorkflowMetadata()
.url`, set in `dist/workflow.js` to `https://$VERCEL_URL` when `VERCEL_URL` is
present and `http://localhost:${await getPortLazy() ?? 3000}` otherwise. There is
no third branch and no `WORKFLOW_BASE_URL`-style variable anywhere in the
installed packages; `getPortLazy` is OS socket discovery and reads no env at all.
The grep missed it because `harness.mjs` bundles the wrong `create-hook` — the
`dist/create-hook.js` THROW-STUB, since the real one is reached only under the
`"workflow"` export condition, which the builder applies and the harness bundle
does not. `hook.url` arrives at runtime from the guest's baked image.

Three consequences, and the second is why interception was rejected:

- **`hook.url` is public API** (`Webhook.url: string`, `@workflow/core`), so it
  cannot be removed from an author's reach — only documented as guest-local,
  which `packages/aai/CLAUDE.md` now does.
- **Interception would mean setting `VERCEL_URL`**, i.e. telling every `isVercel`
  branch in the DevKit that this is Vercel — including the replay watchdog this
  doc already names. `setWorkflowBasePath()` is no help either: it prefixes EVERY
  route, `flow` and `step` included, which the guest would then have to serve at
  the prefixed paths.
- **The premise is pinned as a test**, not taken on trust:
  `dev-workflow.scenario.test.ts`'s callback flow returns `hook.url` and a spec
  asserts it is `http://localhost:<port>/…` carrying the shared webhook prefix.
  An
  upstream change that starts minting a public origin fails there rather than
  leaving the accessor quietly redundant.

### What the implementation found that this plan did not

- **`resolvePublicOrigin(req)` is not available where a spawn happens.** Three of
  the four spawn paths hold no request — the blue-green handover fires off the
  agents-row change stream, the wake sweep off a timer, and the peer route answers
  before either — and `brokerOpts` is assembled once at orchestrator construction,
  so there is no per-request seam to thread. The origin is therefore RECORDED by
  the shared middleware (`rememberPublicOrigin`) and read by
  `agentPublicBaseUrl(slug)`, with `AAI_PUBLIC_ORIGIN` winning as before. That is
  the same one-origin caveat this doc already states, one step earlier, and it is
  why the caveat is worth a sentence in the platform guide rather than a mechanism.
- **`publicUrl` did NOT go on `PassthroughServerOptions`.** That bag exists so a
  hook added to it reaches both wrappers, and neither wrapper can use this:
  `createServer` builds no workflow client (its runtime is handed in) and
  `createHostServer`'s sessions run caller-supplied agents, which declare no
  workflows. It is on `RuntimeOptions` (the reader) and `AgentServerOptions` (the
  front door `server.mjs` uses); anywhere else it would be a field that quietly
  does nothing.
- **The epoch bumps are `--retain`, not `--drop`.** This doc's "What this owes the
  gates" called for `--drop` on the no-backwards-compatibility rule, and that rule
  is about not CARRYING compatibility, where the classification is a factual claim
  about whether earlier authoring still compiles. It does: adding a method to
  `WorkflowClient` breaks no `agent.ts`, and every frozen example from epochs 1-7
  compiles unchanged. `--drop` would have recorded a false claim in a ledger built
  to be read, and would have deleted an example that still passes — while leaving
  epochs 1-6 "supported" beside a dropped 7, which is incoherent. All six previous
  additive `workflow` bumps were retained for the same reason.
- **Five capabilities moved, not one.** `WorkflowClient` is reachable from
  `aai:agent`, `aai:state`, `aai:testing` and `aai:tool` as well (a `ToolContext`
  carries it), and a capability's hash covers types reachable FROM its surface.
  Each
  got a frozen example saying so.
- **A step still cannot reach it.** The accessor is on `ctx.workflows`, so a TOOL
  has it; a `"use workflow"` body and the step it hands `hook.token` to have no
  `ToolContext`. A run that must EMAIL its own callback URL therefore still takes
  the value from its author. `stepEnv`'s `Symbol.for` slot is the shape that would
  close it, and that is a separate change.
- **Two files crossed the 500-line cap** and were split rather than shortened:
  `sdk/workflow-client.ts` now holds the `WorkflowClient` type (leaving
  `sdk/workflow.ts` as the declaration surface, re-exporting it), and
  `host/workflow-wdk-types.ts` holds the WDK seam types — which also stops the
  module that must not reach the engine being the one that declares its shape.
  The rolled-up API report is byte-identical across both moves.

## Declined, with reasons

- **`withEve()`-style co-deployment.** eve's real product difference: keep your
  Next app on your own Vercel project and have the agent be a service behind
  `/eve/v1/*` on your own origin. Our answer is two-part and adequate —
  `server.mjs` for "run the whole thing yourself", and a browser client pointed
  at a deployed slug for "my app talks to a managed agent". The one thing eve
  buys that we cannot is a **first-party origin**: our client already talks to
  two origins (the platform broker, then the sandbox tunnel), so anything that
  wants same-origin cookies or a single CSP source is out of reach. Revisit if
  that becomes a request; it is a routing project, not an adapter.
- **A `GUEST_ROUTE_EXPOSURE`-style declaration for the boot env, as a new
  `guard-invariants` rule.** Note the next free number is **15, not 14**:
  `4-callback-surface-collapse.md` has settled 14 for its `on*` count ratchet,
  and that doc records its own draft having claimed 13 and found it taken. Rule
  IDs are stable and appear in commit messages and in the baseline, so two plans
  reasoning about "the next number" independently is how a collision gets
  committed — this line exists so the ledger has one reader.

  Tempting, and the shape is right — the env is spelled once in
  `warm-harness.ts` and once in `aai-guest/limits.ts`, in two packages that may
  not import each other, which is exactly rule 12's situation. Declined because
  the failure mode is not rule 12's: the seven keys are read at boot and a
  mismatch fails the spawn loudly (`guestUnderstandsBundleUrl` exists for the
  one case that could be quiet), where an undeclared ROUTE 404s and reads to the
  client as a dead sandbox. Rule 12 was worth its number because
  `GET /studio/tools` really had gone missing; nothing here has. If this change
  lands and the boot env starts growing, reconsider — with the note that
  `AAI_PUBLIC_BASE_URL` is the second key in it whose consumer is the BUNDLE's
  SDK rather than the harness, which is a genuinely new direction and the thing
  that would make a declaration earn its keep.
- **Making `_preflight.ts` fail rather than warn**, on the strength of eve's
  prewarm. Its own module doc already argues this correctly: the CLI cannot see
  what `aai secret put` stored, "and a false rejection is worse than a false
  warning: it blocks a deploy that would have worked." eve's prewarm can fail
  because it checks a token it can actually observe.

## What this owes the gates

- **`ctx.workflows.webhookUrl` is a new public export on an authoring subpath**,
  so it joins the `workflow` capability and needs a `--bump aai:workflow`. The
  bump is `--drop` with a reason, not `--retain`, per this directory's
  no-backwards-compatibility rule; the changeset is `minor` (an addition), and
  `major` if the hook's own `url` is changed rather than supplemented.
- **`publicUrl` on `PassthroughServerOptions` is NOT contracted** — `/runtime`
  is in `NON_AUTHORING_SUBPATHS` — but it does move `etc/runtime.api.md` and
  `API-EXPORTS.json`, so `pnpm api-report` runs in the same change.
- **`GUEST_CONTRACT_VERSION` goes 2 → 3**, with the additive-only rule intact,
  and `aai-guest/limits.ts`'s boot-env list gains the key.
- **No new ratchet**, per the decline above — this change consumes no rule
  number, which is what leaves 14 free for doc 4.
- The three deployment paths each owe a line: `aai-server/CLAUDE.md` (the
  one-origin caveat), `aai-guest/CLAUDE.md` (the boot key), and the scaffold's
  `server.mjs` (`PUBLIC_URL`, which is also the first thing in that file a
  container operator has to set).
