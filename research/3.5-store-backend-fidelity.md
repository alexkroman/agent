# Store backends: prove the doubles, don't delete them

The question this answers: *should the in-memory storage go, so that tests and
`aai dev` look like production?*

The instinct is right about the defect and wrong about the lever. The memory
backends are not the problem — the **unverified equivalence** between them and
their Postgres counterparts is, and deleting them would pay for that fidelity
with a mutable external dependency under 49 test files. This proposes proving
the doubles instead: one conformance suite per store contract, run against the
real backend as well as the memory one, plus the five cache/drift defects found
while measuring, which have to be fixed first or every assertion below is
believed rather than true.

**And "a real Postgres" turns out to be a fiction.** CI's is a stock server with
every `create extension` line stripped and pgmq hand-stubbed, so Vault, pg_cron,
pg_net, walrus and Storage have no real arm anywhere — while the local Supabase
stack, twelve Docker containers already running on this machine, has all of them.

That resolves into a rule the plan now runs on: **an arm is legitimate only if
something really runs on it.** Memory qualifies (an agent with no
`DATABASE_URL`); the Supabase stack qualifies (it is the platform); a stock
Postgres qualifies for the SDK's own stores, where a user brings their own
database, and NOT for the platform stores, where no such deployment exists. So
the platform tier gets **one** real arm — the stack — and the plan below deletes
the stock arm along with the extension-stripping and the pgmq stub that exist to
prop it up. There is no PGlite phase: nothing runs on PGlite either.

**Sits after `3-session-event-stream.md`, which is the step in flight.** The
ordering is a real constraint in one direction and not the other. Doc 3 does not
need this plan to ship — but it *adds the next memory/Postgres pair*: a retained
session event stream, explicitly designed as "a second consumer of that store,
not a second store", with the same two backends and the same selection rule. A
new pair with no conformance table is a fidelity hole by construction, and the
table for it can only be written once doc 3 has defined the contract. Hence
3.5 rather than 4: the work belongs immediately behind the thing that creates
its newest subject.

One exception to that ordering, called out in the sequence below: **phases 1-4
are independent of every plan in this directory and should be done during step
3, not after it.** They are hours of work, and doc 3 is about to write Postgres
assertions that phase 1's defect can serve from a stale cache — against a
database phase 2 would have told it was six migrations behind, on a stack phase
4 would have made reachable.

## "Memory storage" is four selectors and thirteen implementations

| Tier | Selected by | Memory | Production |
| --- | --- | --- | --- |
| Session slot state | the AGENT's `DATABASE_URL` (`runtime-session-state.ts:51`) | `createMemoryStateBackend` | `createPostgresStateBackend` |
| Workflow keys / queue world | same | `createMemoryKeyStore` (`workflow-keys.ts:77`) | `createPostgresKeyStore` |
| Platform stores | `isLocalDev` — no `SUPABASE_STORAGE_BUCKET` (`_boot.ts:33`) | agents, workspaces, chats, secrets, blobs, events, slug lock, rate limiter, sandbox directory | Postgres / Vault / Supabase Storage / Realtime |
| Studio | `base.sql` present (`aai-studio-server/index.ts:77,81`) | session registry, preview queue | pg |

Thirteen implementations, ~350 lines between them — eleven named `createMemory*`
plus the two that are not (`localSlugLock`, and `createRateLimiter`, whose
Postgres twin carries the `Pg` prefix instead) — and **49 `*.test.ts` files
construct one**. So "drop it to simplify" removes very little code; what it
removes is one of two code paths, and it charges the whole test tier for the
privilege. (Counts re-measured 2026-08-14: `grep -rho "createMemory[A-Za-z]*"`
for the factories, and the same plus the two odd names across `*.test.ts` for
the consumers. The two unprefixed names are worth knowing before writing the
registry guard in phase 10 — a spec scanning for `createMemory*`/`createPg*`
pairs finds eleven of thirteen and reports the other two as absent contracts.)

## The first two tiers are PRODUCT tiers, not test scaffolding

`sessionSlot` and `ctx.workflows` work for an agent with no database. That is a
shipped promise, documented in `packages/aai/CLAUDE.md`: which backend an agent
gets "is a property of the DEPLOYMENT, never of a slot". Deleting the memory
backend there means every template quickstart and every `aai dev` run needs a
Postgres before a voice agent can hold a cart.

It is also the tier with the LEAST fidelity risk, because it already does the
thing this plan proposes for the others: `freezeStorable` runs in both backends,
so a `Map`, a `Date` or a `NaN` fails in a spec rather than on the first deploy
with a database. `session-state-store.ts`'s header states the reasoning
outright — a per-slot `persist` flag was refused precisely so the memory backend
could not become a laxer one. **That is the model. The platform stores do not
follow it.**

## The parity table already exists, and its "postgres" arm is a JS emulator

This is the finding that reframes the whole question. `workspace-store.test.ts`
already runs its assertions over both implementations:

```ts
// ── Behavioral parity: both implementations must agree ────────────────
const implementations: [string, () => WorkspaceStore][] = [
  ["memory", () => createMemoryWorkspaceStore()],
  ["postgres (fake SqlExec)", () => createPgWorkspaceStore(createFakeSql().sql)],
];
describe.each(implementations)("WorkspaceStore parity: %s", (_name, make) => { … });
```

`chat-store.test.ts` has the same table. So the pattern is invented, named, and
in use — and the arm labelled `postgres` is `createFakeSql()`, a ~64-line
hand-written JS reimplementation of the store's own SQL
(`createDispatchingSql` matching statement prefixes to closures over a `Map`).
It is a THIRD implementation of the contract, it is the one a reader trusts most
because of its label, and it holds JS values — so it cannot represent a single
one of the bugs that have actually shipped:

- **The `::text::jsonb` double-encode.** Bound with a bare `::jsonb`,
  postgres.js re-encodes an already-encoded string and the column holds a jsonb
  *string*. Every metadata stamp raised `cannot delete from scalar`, and the
  orphan-preview sweep read `doc->>'previewSlug'` as NULL and deleted live
  previews. `aai-server/CLAUDE.md` names the cause exactly: "the in-memory
  stores cannot represent the bug… every unit test passed against a shape
  production never had."
- **Three orphan tables** (`sandbox_registry`, `slug_epochs`, `slug_locks`)
  created at runtime, declared nowhere, and therefore the only tables in the
  schema without RLS — invisible to every static check and to every fake.
- **Advisory locks through a transaction-mode pooler**, where the lock is not
  held by whoever thinks it holds it. A fake `SqlExec` has no connection at all.

Every one of those was found in production or by audit. None was found by a
test, and none could have been.

## The "real Postgres" arm is a STOCK Postgres, which is a third emulation

One rung under the fake `SqlExec` sits a second, quieter substitution — and it
is in the arm this plan was going to lean on. `platform-schema.integration
.test.ts` applies "the migration as it ships, minus the two `create extension`
lines", and hand-writes a plpgsql `pgmq.create(text)` so the migration's queue
block can run at all. That is not a degraded fallback path: CI's integration
leg starts the runner's own `postgresql` service
(`.github/workflows/check.yml:219`), so a stock server with no Supabase
extension is the ONLY real database anything here has ever run against.

What that leaves with no real arm anywhere is not marginal:

| Depends on | Real arm today |
| --- | --- |
| `createVaultSecretStore` — `vault.create_secret`, `decrypted_secrets`, `update_secret`, the `23505` retry | none |
| every pg_cron sweep BODY in `platformCronJobs()` | none — `pg-cron.test.ts` captures statement text |
| the migration's pgmq queue block | a hand-written `pgmq.create` stub |
| `pg_net` in the blob GC's delete | nothing calls it; its sweep body is untested anyway |
| walrus / Realtime `postgres_changes` | `realtime-rls.scenario.test.ts`, which runs on no machine (defect 4) |
| Supabase Storage (`blob-storage.ts`) | none |

The pg_cron row is the one to feel, because it contradicts a rule this package
already states. `packages/aai-server/CLAUDE.md`: "anything that reaches into a
jsonb column from inside Postgres — an arrow operator, `-`, `jsonb_set`, a
predicate in a pg_cron body — needs a test against a real database." Every
sweep body does exactly that (`client_files` for the blob GC,
`doc->>'previewSlug'` for the orphan-preview sweep), and not one has ever been
EXECUTED by anything. `pg-cron.test.ts` asserts that
`select cron.schedule($1, $2, $3)` was called with the body as a *parameter* —
a test of the scheduler call, not of the SQL inside it. A sweep body with a
syntax error, or with the double-encode bug reached through an arrow operator,
is green here and wrong hourly in production, silently, since `guarded()`
swallows it.

## The local Supabase stack IS that arm, and it is already running

`supabase start` brings this project's stack up under `project_id =
"aai-platform"`, and the container under all of it is
`public.ecr.aws/supabase/postgres:17.6.1.155` on 54322 — the image the
production project runs, not a stock server. Measured on it while writing
this:

| Extension | Installed | What it unblocks |
| --- | --- | --- |
| `supabase_vault` | 0.3.1 | `createVaultSecretStore`, end to end |
| `pgmq` | 1.5.1 | the queue block, with no stub |
| `pg_cron` | 1.6.4 | EXECUTING a sweep body, not scheduling one |
| `pg_net` | 0.20.4 | the blob GC's delete path |

Plus the services around it, which no Postgres of any kind supplies:
`realtime` v2.112.6 (walrus — the row-visibility filter
`20260807000000_platform_rls.sql` says "cannot be checked from a test suite"),
`storage-api` v1.67.26 (the `blobs/<sha256>` bucket), `gotrue` v2.195.0 (the
session verification in `supabase-auth.ts`), and `kong` fronting them on
54321.

The Vault race is the worked example, because the code's own comment is what
says no fake can hold it — `secret-store.ts`'s `put` "absorbs a lost create
race" by retrying `23505` exactly once, and instructs the reader to read the
SQLSTATE rather than the message. On the local stack that is two statements:

```sql
select vault.create_secret('probe-value', 'zz-probe');
select vault.create_secret('again', 'zz-probe');
-- ERROR: duplicate key value violates unique constraint "secrets_name_idx"
```

The real constraint, by its real name, with the real SQLSTATE — the exact
behaviour the retry exists for, which nothing in this repo has ever observed.

### An arm is legitimate only if something really runs on it

That is the rule this doc was missing, and applying it DELETES more than it
adds. A double earns its place by standing in for a real configuration; an arm
describing a deployment nobody has is one more shape production never had, which
is the exact charge laid against the fake `SqlExec` two sections up.

| Candidate arm | Does anything run on it? |
| --- | --- |
| memory | **Yes** — an agent with no `DATABASE_URL`. A shipped promise (see "PRODUCT tiers" above) |
| local Supabase stack | **Yes** — it IS the platform, on the production Postgres image |
| plain Postgres, for the SDK's own stores | **Yes** — an agent's `DATABASE_URL` may be Neon, RDS, or a laptop server |
| plain Postgres, for the PLATFORM stores | **No.** Nothing anywhere runs `aai_platform` without Vault, pg_cron and walrus |
| PGlite | **No.** Nothing runs on it — not dev, not prod, not a user |
| fake `SqlExec` | Not a database at all — see below |

So **three arms across the repo, and two for any one contract**: memory plus the
stack for everything in `aai_platform`, memory plus a plain Postgres for the
SDK's own stores. No contract gets three, and the fourth candidate an earlier
draft of this doc proposed to spike is gone.

- **PGlite is dominated on both axes.** Its pitch was "Postgres with no service
  to start", and on that axis the thing it must beat is the memory arm, which
  already runs everywhere at a fraction of the complexity. On the other axis it
  cannot approach the stack: single-connection, so advisory locks — the entire
  content of `platform-lock.ts` — are unrepresentable, and no Vault, no pg_cron,
  no walrus. It would be a FIFTH environment invented to sit between two that
  already exist, with failure modes belonging to nothing but itself.
- **Plain Postgres survives only where a plain Postgres is what a USER brings.**
  That is the SDK tier, and there it is the product:
  `session-state.scenario.test.ts` covers `createPostgresStateBackend`,
  which runs against whatever `DATABASE_URL` an agent is handed — a per-app
  schema on the platform, or someone's own server under `aai dev`. Portability
  is the promise, so a stock server is the RIGHT arm there. For the platform
  stores it is a fiction, and the next section prices it.
- **The fake `SqlExec` should stop being an "implementation" at all.** It holds
  no data semantics and never claimed to; what it uniquely asserts is that a
  store issued the STATEMENTS it should have — the `::text::jsonb` cast, and no
  DDL. That is a recorder, and it belongs in its own spec rather than in an
  `implementations` list where a reader compares it against databases. Renaming
  it `sql-shape` was half the fix; taking it out of the parity table is the
  other half.

### What the stock arm costs, now that it defends nothing

Deleting it is not just tidying, because the machinery that exists to serve it
is itself hand-written emulation:

- `platform-schema.scenario.test.ts` strips every `create extension` line
  with a regex, and hand-writes a plpgsql `pgmq.create(text)` — a fourth
  implementation of a contract, in SQL this time, whose own comment concedes it
  is "deliberately not an emulation of pgmq" while being exactly that. Both
  disappear with the arm; the stack has the real extensions.
- Every "which rung does this contract need" decision disappears with it too.
  Vault, pg_cron, Storage and walrus stop being special cases needing a second
  gate; there is one real arm, and a platform contract either has it or has no
  real arm at all.
- `with-test-pg.mjs`'s 5432 candidate stops being a valid answer for the
  platform tier. Resolving a database that cannot run half the suites, and
  saying nothing about it, is the same silent-skip shape as defect 4.

**And the reasoning that produced the stock arm was circular.** `check.yml`'s
own comment: "A step rather than a `services:` container, because those need
Docker and this job's matrix includes macos-latest, where it is unavailable" —
followed two lines later by "the tests skip themselves on macOS, where
`AAI_TEST_PG_URL` is unset". Docker was avoided for a leg that runs none of
these suites. The Linux leg is the only consumer, and Docker is available there.

### CI can run this, and the extension half is ONE `services:` container

The remaining objection to deleting the stock arm was CI, and it does not hold.
Measured locally, on a bare `docker run` of the production image with no
Supabase CLI, no compose file and no stack:

```sh
docker run -d -p 5432:5432 -e POSTGRES_PASSWORD=postgres \
  public.ecr.aws/supabase/postgres:17.6.1.155
# pg_isready: 5s (warm image)
create extension supabase_vault;   -- CREATE EXTENSION
create extension pgmq;             -- CREATE EXTENSION
create extension pg_net with schema extensions;  -- CREATE EXTENSION
create extension pg_cron;          -- CREATE EXTENSION
```

All four install in a plain container, `pg_cron` included — which is the one
that could have failed, since it needs `shared_preload_libraries`, and the image
ships that config. Vault then behaves as production does: `create_secret` writes,
`decrypted_secrets` reads back, and a second `create_secret` on the same name
raises `23505` on `secrets_name_idx`.

So the ubuntu leg's change is one image name. It is a `services:` container —
exactly the shape `check.yml` avoided for a matrix reason that turned out not to
apply — and it needs no CLI, no `supabase start`, and no health-check
choreography beyond the `pg_isready` already there.

That splits the arm into two shapes, and the split is worth being explicit about
because both are configurations something really runs on:

| Shape | Images | Local size | Covers |
| --- | --- | --- | --- |
| `services:` the Supabase Postgres image | 1 | 1.76 GB | Vault, pgmq, pg_cron, pg_net — so secrets and the sweep bodies, two of the four contracts with no arm today |
| `supabase start -x studio,edge-runtime,analytics,imgproxy,vector,rest,meta,inbucket` | 5 | ~3.96 GB | the above + walrus, Storage, Auth |
| `supabase start` (everything) | 12 | ~9.2 GB | + studio, PostgREST, mail, logs |

The first is the default: it is where the extensions live, so it covers
everything the stock server could plus the two contracts it could not (secrets,
and the pg_cron sweep bodies). The second is what the remaining two need —
platform events, i.e. `realtime-rls`, needs walrus; blob storage needs
`storage-api` — and it is a documented CI path: `supabase/setup-cli` plus
`--exclude`, which is a real flag.

**The one number left unmeasured is the COLD pull**, since runners cache no
images between runs; 1.76 GB is the local uncompressed size, and the download is
smaller. Measure it against the ~5.4s the tier costs today. But it is no longer
a question of whether CI *can* — it can, with less machinery than it has now.

## What requiring Postgres everywhere would actually cost

The runtime is not the objection. Measured on this machine against the local
Supabase stack on 54322: `aai-server`'s integration tier is **5.4s**,
`pnpm test:pg` end to end **13s**. Fast enough to be the default if it were
reliable.

It is not reliable, and the run proved it: **1 suite failed —
`column w.preview_slug does not exist`** — because the local database predates
`20260810020000_preview_slug_column.sql`. Not a code bug. The cost of pointing
tests at a real database is that the database is a mutable environment, and this
one had drifted with nothing reporting it: `supabase_migrations
.schema_migrations` holds three of the nine migrations in the repo, so it is
six behind, and `preview_slug` is only the first of the six a suite happens to
touch. Multiply that by 49 files and the failure mode stops being a red suite
and becomes a habit of disbelieving red suites.

**The drift is the stack's one real liability, and it is the argument for
treating it as a declared tier rather than a machine someone happens to have.**
A stack that is six migrations behind is a stack whose extension arms would
report failures that belong to the environment, which is precisely how a
high-fidelity tier loses its credibility.

That drift has a specific, fixable cause, which is the next section.

## Five defects found while measuring, all in the "checks nothing" family

Each is small, each is independent of the design below, and each makes an
assertion further down untrustworthy. They are the front of the sequence.

**1. `supabase/migrations/**` is hashed by no turbo task.** `globalDependencies`
is `pnpm-lock.yaml`, `pnpm-workspace.yaml`, `tsconfig.json`,
`vitest.slow.config.ts` — and `inputs` globs resolve relative to the PACKAGE, so
nothing covers a repo-root directory. Six suites read that directory, including
`platform-schema.test.ts`, which is in the **unit** tier and whose whole job is
to assert every `aai_platform.<table>` the source queries is declared by a
migration. Editing a migration therefore cannot invalidate the cache of the test
that guards migrations, in either tier. Same class as the root `tsconfig.json`
miss and the never-existing `vitest.integration.config.ts` this repo has already
paid for twice; the fix is one `globalDependencies` entry, and the proof is the
documented one — capture `--dry=json`'s hash, touch a migration, capture again.

**2. `ensurePlatformTables` returns early on a database that already has the
schema** (`test-utils.ts:247-252`). The early return is deliberate and its
comment says so: pointing the suite at the local Supabase stack or at staging
"runs no DDL at all". What follows is that the tier asserts nothing about the
schema being CURRENT — it only asserts that *some* `aai_platform` exists. That
is exactly how my run failed, and the failure names a column rather than the
cause, so the first reading is "the code is broken".

**And the local stack hands us an exact oracle for it, which no column
comparison would need to reconstruct.** The CLI records what it applied:

```text
$ select version from supabase_migrations.schema_migrations order by 1;
20260805000000
20260807000000
20260807120000
```

Three of nine. The stack was started before
`20260808120000_agents_config_default.sql` and has never caught up, because
`supabase start` applies migrations on INIT and nothing since has run
`supabase migration up` or `db reset` — so the six newest, including the
`preview_slug` column my run died on, exist only in the repo. The fix is
therefore cheaper and more precise than "diff the columns": when
`supabase_migrations.schema_migrations` exists, compare its version set against
`readdirSync(supabase/migrations)` and fail naming the missing files and the
command that applies them. When it does not exist, the database was built by
this helper's own DDL and the current path is right. Note this also makes
`ensurePlatformTables`'s regex applier — a THIRD thing that applies the schema,
after `supabase db push` and `supabase start` — honest about which of the three
built the database it is looking at.

**3. `studio-session-broker.ts:256` falls back to a memory queue silently.**
`options.previewQueue ?? createMemoryPreviewQueue()` — inside production source,
where every other memory selection in this codebase announces itself with a
`console.info` naming the tier. The composition root already decides
(`index.ts:81` passes `undefined` when there is no `sql`), so the `??` is a
second decision point that can only disagree with the first. Make the choice
explicit at the root and let the broker require its queue.

**4. Nothing RESOLVES the stack, so the suite written for it runs nowhere.**
`realtime-rls.scenario.test.ts` gates on a CONJUNCTION —
`AAI_TEST_SUPABASE_URL` and `_SERVICE_KEY` on top of `AAI_TEST_PG_URL`, plus
`_ANON_KEY` for the negative control — and its own header documents the three
values as something a human pastes from `supabase status -o env`.
`with-test-pg.mjs` probes 54322, names it "Supabase local stack" in the line it
prints, and then exports the database URL alone. So `pnpm test:pg` on this
machine runs that suite's Postgres half and SKIPS the suite: the only test of
walrus, skipped on the one machine in the world that is running walrus. CI
cannot cover for it either — the Linux leg starts a stock `postgresql` service
and `AAI_TEST_SUPABASE_*` appears in no workflow file — and `AAI_REQUIRE_PG`
does not reach it, because that contract was written for the database half.
The resolver should shell out to `supabase status -o env` when its 54322 probe
answers, keeping the same "find one, never start one" contract, one command
wider. Everything needed is in that output: `API_URL`, `SERVICE_ROLE_KEY`,
`ANON_KEY`, `DB_URL`.

**5. `supabase/config.toml` states that the stack does not exist.** Its header:
"The platform does not run a local Supabase stack: dev and tests use in-memory
stores… the only thing the CLI is used for here is migrations", and
`major_version` is annotated "Only used by a local `supabase start`, which this
repo does not require." Both were true when written; neither is now —
`with-test-pg.mjs` lists `supabase start` first among the databases it hopes to
find, `realtime-rls.scenario.test.ts` is written against it, and it is up.
The stale comment matters beyond tidiness, because that file is where a
stack-as-a-tier gets DECLARED, and the two things the plan below wants from the
stack are both config in it:

- **`[db.pooler]`** — `enabled`, `port = 54329`, `pool_mode = "transaction"`.
  The container (`supabase_pooler_aai-platform`) is in the stack and stopped.
  Enabling it makes `assertSessionModeUrl`'s premise DEMONSTRABLE rather than
  merely argued: take an advisory lock through the transaction-mode port and
  show it is not held by the session that thinks it holds it. That is the third
  bug in the list above, and it is the one that has never been reproduced
  anywhere.
- **`[storage.buckets.<name>]`** — so `SUPABASE_STORAGE_BUCKET` resolves
  locally and `blob-storage.ts` has an arm at all.

"Sections for auth/storage/realtime settings are intentionally absent" is the
right instinct about DASHBOARD settings, which are a second source of truth
nothing applies, and the wrong one about the local stack's own shape, which
this file is the only place to state.

## Design

### One conformance suite per contract, over TWO arms

Take the parity table that exists, drop the arm that is not a database, and put
the real one behind it:

```ts
const implementations = [
  ["memory", () => createMemoryWorkspaceStore()],
  ...(STACK ? [["supabase", () => createPgWorkspaceStore(stackSql)]] : []),
];
// The fake SqlExec keeps its own spec — the statements this store issues, and
// the DDL it must never issue. It is a recorder, not a third implementation.
```

Two arms, because there are only two configurations anything runs on: an agent
with no database, and the platform. Three properties make this worth the work
rather than ceremony:

- **The arm list becomes the only place the contract is asserted.** Today
  `agent-store.test.ts` has two separate `describe`s (`createMemoryAgentRows`,
  `createPgAgentRows`) asserting different things, and
  `platform-schema.scenario.test.ts` asserts a THIRD set against real
  Postgres ("agents rows round-trip", "a re-put bumps version", "delete removes
  the row and its version"). Three spec sets over one contract, free to drift,
  and the drift is silent because each is internally green.
- **Only the stack arm is gated; memory stays unconditional.** This matters
  mechanically: per-package coverage floors are what gate a PR, so a suite whose
  assertions only execute with a database in reach would drop `aai-server`'s
  measured coverage on every machine without one. Memory keeps covering the
  code; the stack adds the semantics it cannot hold. The recorder spec is
  unconditional too, for the same reason.
- **A NAMED gate is what stops the stack's absence being invisible.** The stack
  arm has the same failure mode the whole plan is about — it skips, quietly, and
  a green run looks identical. So it announces itself the way `describeWithPg`
  does (`describeWithStack`, one spelling, printing how to get one), and an
  `AAI_REQUIRE_STACK` escalation makes a dropped variable red rather than green
  wherever it is meant to run. With no fallback arm this gate is now the only
  thing standing between "the platform tier ran" and "the platform tier was
  absent", so it carries more weight than `describeWithPg` ever did.

Stores with a pg implementation and **no** parity table at all today: agents,
secrets/Vault, blob storage, rate limiter, sandbox directory, studio session
registry, preview queue, slug lock. Each gets one, in the order of the sequence
below — highest first by "what would a wrong answer cost", not by size.

**Collapsing to one real arm is what makes that list uniform.** The earlier
draft ranked each contract by the lowest rung that could hold it, which was a
table of exceptions: plain SQL here, Vault there, walrus somewhere else. With
one arm the rule is flat — every platform contract's real arm is the stack — and
what is left worth recording is the four that had no real arm at all before,
because they are what the arm is FOR:

| Contract | What only the stack can hold |
| --- | --- |
| secrets | Vault: `create_secret`, `decrypted_secrets`, the `23505` on `secrets_name_idx` |
| pg_cron sweep bodies | `cron.schedule` plus a body that touches jsonb — nothing executes one today |
| blob storage | `storage-api`, a real bucket, `createSignedUrl` |
| platform events | walrus — already written (`realtime-rls`), already skipped |

The pg_cron row is the one that is not a store at all, and it should still be
in this list: the sweeps are code that runs against production data hourly with
`guarded()` swallowing whatever it raises. On the stack, `platformCronJobs()`
can be scheduled for real and each body EXECUTED once against a seeded schema —
which is the only thing that can distinguish "this SQL is valid" from "this SQL
was passed to `cron.schedule` as a string".

**Doc 3's event-stream backend inherits the same two arms**, and that is now a
decision it does not have to make: whatever its Postgres half turns out to be,
its real arm is the stack, because that is where its Postgres half will run.

### The registry needs a static guard, because an empty table passes

A conformance table that lists only its memory arm reports the same green as one
listing both; a contract nobody registered reports nothing at all. Collapsing to
two arms makes this MORE load-bearing, not less — there is no third arm left to
notice the absence of the second. That is the
gate-under-the-gate rule this repo applies to `api-surface-file.test.ts` and
`api-contracts-gate.test.ts`, and it applies here: a spec in `aai-server`
scanning source for `createPg*`/`createMemory*` pairs and asserting each pair
appears in the conformance registry. `platform-schema.test.ts` already does
static source scanning in this package, so there is a home and a pattern.

Not a `guard-invariants.mjs` rule: the check is a set comparison over exported
symbols, not a text pattern, and rule 14 would have to be written as a regex
over two files that must AGREE — which is the shape `guard-invariants-scanners.mjs`
exists for and still awkward. A test is the right instrument.

### Dev parity is one branch, and it is currently the wrong way round

`service-config.ts:266` — with `SUPABASE_DB_URL` set but no
`SUPABASE_STORAGE_BUCKET`, local dev takes the memory stores for agents,
workspaces, chats and secrets **even though a Postgres is right there**, while
happily using that same database for per-app schemas and the wake sweep two
lines later. Prefer the pg stores whenever a DB URL is present. Blob storage
stays memory (it keys off the bucket, correctly), and `isLocalDev` keeps
selecting the subprocess sandbox backend and dev auth — those are separate
questions and must not ride along.

That is most of the "dev like prod" the question was after, for one branch: full
parity is already reachable today by also setting `SUPABASE_STORAGE_BUCKET`, and
nothing says so anywhere. It should be a documented dev mode with a name.

**With the stack running, that mode is no longer a thought experiment — every
value it needs is one command away.** `supabase status -o env` prints `DB_URL`,
`API_URL`, `SERVICE_ROLE_KEY` and `PUBLISHABLE_KEY`, which is exactly
`SUPABASE_DB_URL` + `SUPABASE_URL` + `SUPABASE_SERVICE_ROLE_KEY` +
`SUPABASE_PUBLISHABLE_KEY`; add a declared bucket (defect 5) and
`SUPABASE_STORAGE_BUCKET` resolves too. Then local dev runs the pg stores, real
Vault, real Realtime and real Storage — the whole production composition, on
this laptop, against migrations you can reset in seconds.

**And that is where `isLocalDev` becomes the blocker rather than a detail.**
It is `AAI_LOCAL_DEV === "1" || !SUPABASE_STORAGE_BUCKET` (`_boot.ts:32`), so ONE
variable decides three unrelated things: which stores are selected, which sandbox
backend runs (`subprocess` versus real Modal), and whether API keys are verified
against AssemblyAI. Setting the bucket to get prod-shaped stores therefore also
demands Modal tokens and a real AssemblyAI key — and the shape a developer
actually wants ("production stores, local sandbox") is not expressible at all.
One boot-time guard interacts with it and does so correctly, which is worth
recording because it is the kind of thing that blocks a mode like this:
`assertServiceRoleKey` refuses only a definitely-anon key, and the stack emits
both credential generations — `SERVICE_ROLE_KEY` as a legacy JWT (measured:
`{"iss":"supabase-demo","role":"service_role"}`, so it passes) and `SECRET_KEY`
as `sb_secret_…`, which is the form production holds and therefore the one this
mode should use. `assertSessionModeUrl` is the one to watch instead: it is
skipped under `isLocalDev`, so splitting that flag means a prod-shaped local run
starts asserting session mode about `DB_URL` — correctly, since 54322 IS a
direct connection, but only as long as the pooler port (defect 5) is not the one
handed over.

So the branch fix and the named mode are really one change with two halves:
prefer the pg stores whenever a DB URL is present (independent of the bucket),
and split `isLocalDev`'s three questions so a dev can answer them separately.
The second half is the one worth designing, not just doing — the bucket-implies-
production coupling is load-bearing security today ("production can never
resolve the host-local backend"), and it must survive being split.

### Deleting the doubles: the question the arm rule settles, and the one it leaves

The earlier draft of this section proposed a PGlite spike so that the memory arm
could eventually be deleted. Both halves of that are now answered, in opposite
directions.

**PGlite: no, and not later either.** Not a deferred spike, not a trigger
condition — it fails the arm rule outright (nothing runs on it), and the two
things it was meant to buy are each already better served: "runs on every
machine" is the memory arm, and "real Postgres semantics" is the stack. A
socket shim would be new code whose failures belong to no deployment. Removing
it from the plan is the point; leaving it as "worth a spike" is how an invented
environment gets built eighteen months later by someone reading this file.

**Memory: it stays, and the rule says why.** The question "can the double be
deleted once the real arm is trusted" was the wrong question, because the memory
backends are not doubles at ALL for the first two tiers — an agent with no
`DATABASE_URL` really runs them, in every quickstart and every `aai dev`
session. They are a shipped configuration with a test, not a test standing in
for a configuration. Nothing about a better real arm changes that.

What DOES stay open is narrower and worth stating as such: the **platform**
stores' memory implementations (agents, workspaces, chats, secrets, blobs,
events, slug lock, rate limiter, sandbox directory) are selected only by
`isLocalDev`, so unlike the SDK tier there is no deployment that runs them
except a developer's laptop. If the dev-parity work below lands — prod-shaped
dev backed by the stack — then that laptop stops running them too, and those
nine become genuine doubles with no configuration behind them. THAT is the
deletion worth revisiting, and the trigger is the dev mode being the default
rather than a quarter passing.

## Sequence

Each phase is independently shippable and leaves the tree better than it found
it. The order is by "what makes the next phase's assertions trustworthy".

1. **Hash the migrations.** One `globalDependencies` entry. Until this lands,
   every migration-guarding suite can be served from cache exactly when a
   migration changed — including the one this plan adds arms to.
2. **Make `ensurePlatformTables` verify instead of assume**, against
   `supabase_migrations.schema_migrations` where it exists. Turns "your database
   is stale" from a `PostgresError` naming a column into a sentence naming the
   six files and the command. Without it, the red runs from phases 7-9 get
   attributed to the code — and on this machine they WILL be red, because the
   stack is six migrations behind right now. (CI is unaffected: a fresh
   container per run cannot drift. This defect is local-only, which is exactly
   why it needs a sentence rather than a stack trace.)
3. **Delete the silent memory fallback** (`studio-session-broker.ts:256`), and
   make the composition root's choice explicit. Small, self-contained, and it
   removes a way for phases 7-8 to be measuring the wrong implementation.
4. **Resolve the stack, don't just find its port.** `with-test-pg.mjs` shells
   out to `supabase status -o env` when 54322 answers and exports the Supabase
   trio alongside `AAI_TEST_PG_URL`; `describeWithStack` becomes the one
   spelling of the gate, with an `AAI_REQUIRE_STACK` escalation to match. This
   is the cheapest phase with the largest immediate effect: it takes
   `realtime-rls.scenario.test.ts` from "runs nowhere" to "runs on every
   machine with the stack up", and it is the prerequisite for every stack arm
   below. It must still not START the stack — but the reason is now cost and
   consent, not the macOS matrix, which runs none of these suites either way.
5. **Switch the Linux leg's image.** `services:` the Supabase Postgres image in
   place of `systemctl start postgresql` — one image name, no CLI, verified to
   install all four extensions in a plain container. Record the cold pull against
   today's ~5.4s tier in the same PR, because that is the only number still
   unmeasured and it is the one a future reader will want. Everything below
   becomes trustworthy as a merge gate at this point and not before.
6. **Delete the stock-Postgres arm and its emulation machinery.** The
   `create extension` stripping regex and the hand-written `pgmq.create` stub
   come out of `platform-schema.scenario.test.ts`, and 5432 stops being an
   answer for the platform tier (it stays valid for the SDK tier —
   `session-state.scenario.test.ts` — where a plain Postgres is what a user
   brings). Rides immediately behind phase 5: the stripping exists only because
   the arm could not install extensions, and after phase 5 it can.
7. **Add the stack arm to the two tables that exist** (workspace, chat), and
   move the fake `SqlExec` out of the arm list into its own recorder spec. Fold
   `platform-schema.scenario.test.ts`'s per-store round-trip specs into the
   table so the assertions stop being three sets. This is the phase that either
   finds something or proves the doubles honest for those two contracts — and
   the jsonb history says workspace is where to start.
8. **Build the tables the other stores have none of**, in this order: agents
   (deploy ownership and the `version` invalidation signal — a wrong answer
   serves superseded code), **secrets/Vault** (the lost-create race the `put`
   comment describes — now a two-statement reproduction, and the first contract
   that could not have been covered before phase 4 at all), rate limiter (an
   atomic upsert under contention — the abuse control is worthless if it is not
   atomic), then session registry, preview queue, blob storage, sandbox
   directory. **And doc 3's event-stream backend as soon as it exists** —
   FIRST in this list if doc 3 has landed by then, because it is the only pair
   whose behaviour nothing anywhere has verified twice; the other eight at least
   have an integration suite or a fake to disagree with.
9. **Execute a pg_cron sweep body**, once. Not a store contract at all, which is
   why it is its own phase: it is the largest untested surface the stack unlocks,
   and the cheapest possible version (schedule `platformCronJobs()`, seed a
   schema, invoke each body once, assert what it deleted) is worth more than a
   conformance table for a store whose SQL was never in doubt.
10. **Register-or-fail guard.** The static spec asserting every
    `createPg*`/`createMemory*` pair is in the registry, so contract number
    fourteen cannot arrive unparried. One arm rule to enforce rather than a
    per-contract ranking: a pg implementation with no stack arm fails.
11. **Dev parity branch** (`service-config.ts:266`) plus a named, documented
    prod-shaped dev mode, backed by the stack (`supabase status -o env` →
    the four variables) and by declaring a bucket + the pooler in
    `config.toml`. Deliberately after the conformance work: this is what starts
    exercising the pg stores under `pnpm dev:aai-server`, and it should land when
    their behaviour is pinned rather than before. The `isLocalDev` split is the
    design half of this phase, not an afterthought.
12. **Pooler demonstration** — enable `[db.pooler]` and write the one test that
    shows an advisory lock through transaction mode is not held by the session
    that thinks it holds it. This turns `assertSessionModeUrl`'s premise from
    prose into a fact, and it is the only one of the three shipped bugs at the
    top of this doc still without a reproduction.

Phases 1-4 are hours (4 is a shell-out and a gate helper). Phase 5 is a
measurement and phase 6 is a deletion that depends on it. Phase 7 is the one
worth doing carefully; 8 is mechanical repetition of whatever shape 7 settles
on. Phases 9 and 12 are each a single test covering something nothing covers.
There is no PGlite phase, deliberately — see above.

**Phases 1-10 are implemented**; the rules they establish are in
`packages/aai-server/CLAUDE.md` ("Two arms per store contract") and this doc keeps
the argument. What landed, and what it found:

- The turbo miss is fixed and was DEMONSTRATED first — `aai-server#test`'s hash
  was byte-identical across a touched migration.
- `ensurePlatformTables` now names the six pending files; the stack was applied
  and the tier went from **55 passed / 10 skipped** to **99 passed / 0 skipped**,
  plus a new 16-test studio scenario tier. `realtime-rls.scenario.test.ts` runs
  for the first time on any machine.
- Four defects came out of running the arms rather than arguing about them, and
  each is the kind only a real arm can see: `jsonb-encoding` wrote a chat with no
  parent workspace (green only because the partial DDL replay omits the
  `do $$`-block foreign key); `realtime-rls` inserted `agents.config`, a column
  dropped six migrations ago; `createPgRateLimiter.check` silently IGNORES the
  `now` its own interface declares, so a shared case passing one reported that
  arm as broken; and the registry guard found `session-state` and
  `workflow-keys` — two SDK pairs nobody had registered — on its first run.
- Two of the plan's claims were wrong about the code, both structural. `services:`
  is per-JOB and the integration matrix still includes macOS, so the Linux leg
  stays a `docker run` STEP with the production image (and `pg_isready` alone is
  a false ready on it — the entrypoint restarts Postgres). And `pg_cron` is a
  single-database extension pinned to `cron.database_name`, so a throwaway
  database omits exactly that one `create extension` line — counted, with nothing
  stubbed. `supabase_vault` turned out to be created by NO migration at all.

**Phases 11 and 12 are NOT implemented.** The dev-parity branch and the
`isLocalDev` split (11) change production store selection and a flag that decides
three unrelated things, one of them load-bearing security; the pooler
demonstration (12) needs `[db.pooler]` enabled and a stack restart. Both are
declared in `supabase/config.toml` now — the bucket and the pooler — so the
config half of each is in place and the code half is not. Frontmatter still reads
`issue: TODO`, which rule 10 accepts and which remains the thing this doc owes.

## Open questions

- **Does the stack arm run in CI's unit matrix or only the integration leg?** The
  integration leg already sets `AAI_REQUIRE_PG`, so the arm is enforced there.
  Running it in the unit matrix as well would double the store assertions per
  PR for a real fidelity gain and a container in every matrix entry. Leaning
  integration-only, but that means a conformance failure is one tier removed
  from the developer who caused it. (With one arm this also decides where the
  ONLY real coverage of the platform stores lives, which raises the stakes of
  answering it "integration-only".)
- **Where does the schema-per-suite fixture live?** `session-state.integration
  .test.ts` builds its own (`drop schema … cascade`, `create schema`, a second
  handle with `search_path` pinned as a guest's role is) and it is the right
  shape. Eight more suites should not each rewrite it — but it belongs in
  `aai-server` while `aai` may import no sibling package, which is precisely why
  `session-state.scenario.test.ts` cannot reach `describeWithPg` today. That
  duplication is already accepted; adding eight more copies is not.
- **What does the cold image pull cost the Linux leg?** The last unmeasured
  number, and the only reason phase 5 is a measurement rather than a one-line
  diff. Answered by shipping it, not by deliberating: 1.76 GB uncompressed
  locally, less over the wire, against a tier that runs in ~5.4s today. If it
  turns out to dominate the job, the fallback is a Linux-only stack leg outside
  the required set — never a fictional arm kept for the appearance of coverage.
- **Do the three service-dependent contracts get their own CI leg?** walrus,
  Storage and Auth need containers the database image does not carry, so they
  need `supabase/setup-cli` + `supabase start -x …` (~4 GB) where the other nine
  contracts need one `services:` line. Both shapes are legitimate under the arm
  rule — each is something that really runs — so this is a cost question, not a
  fidelity one. Leaning: database image on the existing leg, trimmed stack on a
  second Linux-only job, so the cheap nine are never gated behind the expensive
  three.
- **Whatever the answer, the run must PRINT the arm it reached.** A tier whose
  fidelity differs between a laptop and CI, silently, is the shape every defect
  in this doc has. `with-test-pg.mjs` already prints what it resolved; it should
  name what that resolution CAN cover, the way the boot log names the sandbox
  backend and why.
- **Does the stack's staleness become a third baseline to maintain?** Phase 2
  makes a stale local stack fail with a sentence, which is the right failure —
  but a developer who has to run `supabase migration up` before every red run
  will learn to distrust red runs, which is the cost this doc priced at the
  start. Options: have the fixture apply pending migrations itself (making it a
  fourth thing that applies the schema — worse), or have it fail with the exact
  command and accept the friction, or reset the whole stack per run
  (`supabase db reset`, seconds, but it discards whatever the developer had in
  it). Leaning "fail with the exact command", because it is the only one that
  cannot surprise anybody.
- **Is `platform-lock` conformable at all?** Its memory arm is
  `localSlugLock` — an in-process keyed lock — and its pg arm is an advisory
  lock on a reserved connection. They agree on mutual exclusion within one
  process and on nothing else; the interesting half of the pg one is
  cross-process, which no shared table can express. It may belong on the list
  as "conformance covers the timeout contract only", with the cross-replica half
  staying where it is in `platform-lock.scenario.test.ts`.
