# Cut the tiers by capability, and delete the tier that never ran

Five tiers are documented in `AGENTS.md`; an eighth exists in the tree and has
never been run by anything. The five that do run are separated by **timeout** —
5s unit, 30s integration, 300s e2e — which is a proxy for the thing that
actually distinguishes them and stops being one as soon as two tests are slow
for unrelated reasons. This proposes re-cutting the boundary by what a test is
allowed to TOUCH, deleting one tier outright, and turning one of eve's guards
into rule 14.

Read against eve (`~/Code/eve`), whose four tiers are declared as a capability
ladder and whose `AGENTS.md` states the selection rule in one line — *"pick the
tightest tier that can express the assertion"*:

| eve tier | Membership rule | Files | Timeout | Retry |
| --- | --- | --- | --- | --- |
| unit | no filesystem writes, subprocesses, or real network | 839 | 5s | — |
| integration | multiple modules **in memory** | 87 | 30s | — |
| scenario | real subprocess, HTTP port, or bundler | 75 | 120s | — |
| e2e | fixture-owned `eve eval` suites, **CI-only** | — | — | — |

Ours, for the same three columns: ~385 unit files, 17 integration, one e2e file
holding four tests. And `retry: 2` on the integration tier, against eve's none.

The point is not that eve has more tests. It is that **a membership rule you can
apply to a test you are about to write** does work that a timeout cannot. Under
ours, `pipeline-fuzz.integration.test.ts` — a pure in-memory property test — and
`platform-schema.scenario.test.ts` — which needs a running Postgres — are the
same tier, share one 30s timeout, share one retry policy, and run in one serial
block. Neither is configured for its own failure mode because the tier cannot
tell them apart.

## Cut 1 — the mutation tier has never run, and cannot be a gate

Not in the `AGENTS.md` tier table, and not in anything else:

```text
stryker.base.config.mjs    stryker.config.mjs      stryker.cli.config.mjs
stryker.host.config.mjs    stryker.sdk.config.mjs  stryker.server.config.mjs
stryker.studio.config.mjs  stryker.ui.config.mjs                8 config files
test:mutate + 6 per-package variants                             7 npm scripts
@stryker-mutator/core, @stryker-mutator/vitest-runner            2 devDeps
```

Grepped `scripts/check.sh`, every file under `.github/workflows/`, `turbo.json`,
`lefthook.yml`, and all nine guides: **zero references.** `stryker.config.mjs`
declares `thresholds: { high: 70, low: 50, break: 40 }` against no committed
baseline.

**It cannot be wired, and the reason is not speed.** `stryker.base.config.mjs`
sets `inPlace: true`, so Stryker mutates the real working tree and restores it
from `.stryker-tmp/backup-*` when the run ends. That is forced rather than
chosen — TS 7 removed the JS API (`ts.parseConfigFileTextToJson`) that Stryker's
sandbox tsconfig preprocessor calls, so sandbox mode crashes; in-place skips the
preprocessor. The same TS 7 constraint that makes `docs/` pin `typescript@6`.
A check that edits the tree it is checking cannot be a pre-push hook, cannot
share a CI checkout, and cannot run beside vitest — the config says so itself.
Its documented side effect is that `packages/aai-cli/bin.mjs` returns with mode
644, so the published bin loses its executable bit if committed after a run.

**Speed is the second reason, and the fix was already attempted.**
`incremental: true` is set in the base config with a distinct `incrementalFile`
per scope — precisely the mechanism for "too slow to run every time". It cannot
work: `.gitignore:28` is `.stryker-incremental*.json`, so the state never leaves
the machine and CI starts cold on every run. Committing it means a 2.1 MB JSON
that churns on every source edit; caching it means a mutation baseline that goes
stale silently, which is the exact failure shape this repo has now paid for four
times (the `.turbo` path that matched nothing, the `.tsbuildinfo` cache in the
job that never wrote it, the silent pg skip, `describe.each([])`). A `break: 40`
served from a stale incremental file prints a score for code it never mutated.

Scope size decides what is even runnable:

| Scope | Source lines |
| --- | --- |
| host | 29,376 |
| ui | 9,890 |
| studio | 7,118 |
| cli | 1,792 |
| server | 1,521 |
| sdk | 689 |

At typical mutant density the host scope is thousands of mutants, each running
its covering tests at `concurrency: 4` under `timeoutMS: 60000`. Hours. The sdk
scope is minutes.

**The archaeology explains the shape.**
`docs/superpowers/plans/2026-04-14-security-mutation-hardening.md` planned one
NARROW security scope at `break: 70`, wired into `check.sh`'s CI branch as its
"Step 4". Step 4 never landed — there is no `stryker.security.config.mjs` and no
`test:mutate:security` script — but the run happened:
`.stryker-incremental-security.json`, 944 kB, dated Apr 14, an orphan state file
for a config that does not exist. What survives in the tree is eight configs for
the BROAD scopes that were never the plan's target.

So: **mutation score is a diagnostic, not a tier**, and the proposal is to say so
rather than to keep an unwired gate.

- Delete `stryker.{host,server,cli,ui,studio}.config.mjs` and their five scripts.
- Keep `stryker.base.config.mjs`, `stryker.sdk.config.mjs`, `test:mutate:sdk`.
  689 lines, minutes not hours, over `protocol.ts` / `manifest.ts` /
  `_internal-types.ts` / `system-prompt.ts` — the schema core.
- Drop `thresholds`/`break` from the kept config. A threshold nothing enforces
  reads as a gate.
- Delete the two orphan `.stryker-incremental*.json` blobs.
- Document it in `AGENTS.md` in one paragraph as a manual diagnostic, explicitly
  NOT a tier and NOT a gate, naming the `inPlace` hazard. An undocumented tool
  is how this reached eight configs.

Note the cheap half is already wired and is not redundant with it:
`check:test-assertions` catches a test with NO assertion; mutation catches an
assertion that does not DISCRIMINATE. Only the first is affordable per-PR.

One concrete payoff for keeping the sdk scope: `3.1-redundant-surface-pins.md`
Cut 3 removes `protocol-snapshot.test.ts`'s inline error-codes snapshot on the
argument that `protocol-compat.test.ts` covers it better. A mutation run over
`protocol.ts` answers whether the snapshot kills mutants the fixture does not —
evidence in place of reasoning.

## Cut 2 — `test:unit` is an alias of `test`

Both are `turbo run test`. Two names, one tier, and the name asserts a boundary
that does not exist. In eve `test` is unit + integration and `test:unit` is
genuinely narrower. Delete ours.

## Cut 3 — split integration into integration and scenario

Measured on this tree, `pnpm test:integration`:

```text
aai-server:check:integration
  Test Files   1 failed | 2 passed | 7 skipped (10)
  Tests        8 failed | 4 passed | 50 skipped (63)
  Duration     721.15s
Tasks: 8 successful, 9 total   Time: 12m9.482s
```

**The eight failures are the `3-session-event-stream.md` work in flight**, not a
standing tier defect — they land in `ws.scenario.test.ts` at
`wireSessionSocket (aai/host/ws-handler.ts:382)`, and both files are modified.
The tier caught real breakage and gets credit for it.

What is structural is the rest: **721 seconds to evaluate twelve tests**, because
50 of 63 skipped for want of a Postgres. The default local invocation of this
tier exercises 19% of it. That is `describeWithPg` behaving exactly as
designed — it ANNOUNCES, which is the whole point — but the design goal was "a
silent skip is the worst outcome available", and the outcome now is a loud skip
that still costs twelve minutes.

The 17 files are three populations wearing one config:

| What it needs | Files | Belongs in |
| --- | --- | --- |
| a real Postgres | 7 (`describeWithPg`) | scenario |
| a real WS server, subprocess, or bundler | 7 (aai-server ws / orchestrator / workspace-build, 2 aai-cli) | scenario |
| nothing but memory and time | 3 (`pipeline-fuzz`, `s2s-fuzz`, `pipeline-reference`) | integration |

The three fast-check harnesses are in the slow tier because they are SLOW, not
because they touch anything. They inherit a 30s timeout they do not need, a
retry policy they must not have (see Cut 4 — their documented contract requires
per-run teardown), and a queue position behind seven suites that want a database.

Proposed: `*.scenario.test.ts` as a third naming convention, selected by a
`scenario` profile in `vitest.slow.config.ts`, membership rule stated in
`AGENTS.md` in eve's words. The integration tier then means what eve means by
it — multiple modules in memory — and `test:pg` becomes a deliberate invocation
of a tier rather than the only way to stop most of one from skipping.

**This does not touch which ARMS exist.** `3.5-store-backend-fidelity.md` owns
that question and answers it ("an arm is legitimate only if something really runs
on it", one real platform arm — the Supabase stack). This plan owns only which
TIER a test sits in. The two compose: once the pg suites are the scenario tier,
3.5's conformance suites have an obvious home and the stock-Postgres arm it
deletes stops being load-bearing for the default local run.

## Cut 4 — drop `retry: 2` from the integration profile

`vitest.slow.config.ts:5`:

```ts
integration: { timeout: 30_000, hookTimeout: 30_000, retry: 2 },
e2e:         { timeout: 300_000, hookTimeout: 300_000, retry: 0 },
```

eve sets `retry` in none of its three tier configs — `vitest.unit.config.ts`,
`vitest.integration.config.ts`, `vitest.scenario.config.ts` carry timeouts only.

A tier that retries has classified its own failures as noise, which is in direct
tension with the rule the rest of this repo's gates are built on. The specific
flakes it was absorbing are documented and were FIXED — the pipeline timing specs
that "failed first on a contended runner" now run on virtual time — so what it
covers today is whatever arrived after, invisibly. It is also a 3× multiplier on
the cost of finding out: much of the 721 seconds above was re-running eight
already-established failures.

Two things make dropping it safe rather than brave. `retry` interacts badly with
the fast-check harnesses in the same profile, whose contract is that per-run
state is torn down in a `finally` — a retried property run is the documented way
to converge the shrinker on the wrong counterexample. And the split in Cut 3
gives the genuinely environment-dependent suites their own profile, so if any
retry is still wanted it can be argued for on the scenario tier alone, with the
in-memory tests out of its blast radius.

## Cut 5 — the e2e tier's skip is a regex over error text

Four tests in 698 lines, three able to self-skip through
`isRegistryProxyFailure(err)` — a regex over
`ECONNREFUSED|…|fetch failed|network`. Narrowing to pnpm-only was right and is
not revisited here. The residual has the shape this repo distrusts everywhere
else: a genuine dependency-resolution break whose error text happens to contain
`fetch failed` skips visibly instead of failing.

eve resolved the same tension the other way — e2e is CI-only by design ("E2E
suites cannot run locally and must run in CI"), fixture-owned eval suites under
`e2e/fixtures/*/evals/`. With no local path to accommodate, no heuristic is
needed. Ours tries to be both locally runnable and trustworthy in CI, and the
error-string matcher is the compromise.

Proposed, in preference order: make the mock-registry install a hard requirement
in CI (`AAI_REQUIRE_REGISTRY`, the same shape as `AAI_REQUIRE_PG`) so the skip
survives only on a developer machine; failing that, narrow the predicate to the
transport-level errno set and drop `fetch failed|network`, which are the two
substrings a real 404 can carry.

## Cut 6 — delete the root coverage thresholds, keep the type projects

`vitest.config.ts` already admits both facts in its own comments: nothing in the
repo or in CI evaluates the root `thresholds` block, and the `aai-types` /
`aai-ui-types` projects are not what gates a `.test-d.ts` (`turbo run typecheck`
is, via TS2344).

They differ in what remains. The type projects keep a real use — `--project
aai-types` is the fast way to iterate on one package's type tests — so they stay.
The four threshold numbers have none: no process reads them, ever, and they are
kept on the argument that they are "the only floor that sees the repo as one
program", which is a view nobody's pipeline takes. Delete them and keep the
measured actuals in a comment, which is the part that was actually informative.

## Steal from eve: rule 14, a fixture directory nothing reads

eve runs `guard:fixtures` (`scripts/guard-test-fixtures.mjs`), which fails CI if
a committed fixture tree appears under `packages/eve/test/fixtures/`, pointing
the author at inline `ScenarioAppDescriptor` objects instead.

We do not want their rule — our fixture trees are legitimate — but we want the
shape. `packages/aai-server/compat-fixtures/` outlived its only reader
(`sandbox-compat.test.ts`, deleted in `30914c9b`) by five commits, and is cited
BY NAME in the `turbo.json` comment justifying that task's cache inputs. So the
generalized rule is **a fixture directory no source file reads**, at rule 14 —
the next free number.

Per `research/README.md`, as a rule in `guard-invariants-rules.mjs` this costs no
new script, no new baseline file, no CI wiring and no new gate-under-the-gate
spec; all four already exist there. It also turns
`3.1-redundant-surface-pins.md` Cut 4 from a one-time deletion into a standing
check. Note the rules module matches most of its own rules, so a rule whose
`label` names fixture directories needs the `SELF_REFERENTIAL` treatment — that
trap has now been paid for four times.

## What is NOT proposed

- **No new tier.** `5-behaviour-eval-tier.md` proposes one, and it is the right
  shape (eve's e2e is exactly that: eval suites over observable behaviour). This
  plan only re-cuts the four that exist. The ordering matters — see below.
- **No change to the pg arms**, per Cut 3. That is `3.5`'s.
- **No revisiting pnpm-only e2e.** `publint` + `attw` cover what the deleted
  npm/yarn legs guarded, and that reasoning stands.
- **No coverage floor changes.** Cut 6 deletes floors nothing evaluates; every
  per-package floor — the ones that gate a PR — is untouched.

## Ordering

The number is weak on purpose and the text says which parts are constrained:

- **Cuts 1, 2, 5, 6 and rule 14 are fully independent** and can land now. None
  touches the protocol work in flight.
- **Cut 3 and Cut 4 want `3-session-event-stream.md` green first** — not because
  they depend on it, but because its eight current failures are the only thing
  making the tier's real timing unmeasurable.
- **All of this belongs before `5-behaviour-eval-tier.md`.** That is the one real
  ordering constraint here: a fifth tier defined against a ladder whose rungs are
  timeouts inherits the defect, and it is much cheaper to state the membership
  rule once than to retrofit it across five tiers.

## What this owes the gates

- **No new public export**, so no capability joins and no epoch bump. This plan
  deletes configuration and moves test files between tiers.
- **Rule 14 is an addition to `guard-invariants-rules.mjs` at the next free
  number**, starting at zero occurrences after `3.1` Cut 4 lands — enforced
  absolutely, like rules 1, 7, 10, 12 and 13, with no baseline entry.
- **No ratchet moves down**, so no `--update` is owed. Worth re-checking after
  Cut 1: deleting five stryker configs removes five root-level `.mjs` files from
  the set `check:file-length` measures via `scripts/*.mjs`, and unclaimed
  headroom WARNS.
- **`pnpm check:knip` after Cut 1.** Removing the last consumer of
  `@stryker-mutator/core` and `@stryker-mutator/vitest-runner` strands two
  devDependencies and their lockfile trees — the documented failure mode of any
  change that deletes rather than adds.
- **A new tier means new turbo wiring, and the `env` rule applies.** A
  `check:scenario` task needs `VITEST_PROFILE`/`VITEST_INCLUDE` in its own `env`,
  not `globalPassThroughEnv`: a variable that selects what a task DOES belongs in
  the hash, or a scenario run and an integration run share a cache entry.
- **`pnpm changeset add --empty`.** Config and tests only.

## Verification

Each claim is reproducible, and the two that matter most are negative:

```sh
# Cut 1: nothing references the mutation tier (expect no output)
grep -rn "test:mutate\|stryker" scripts/check.sh .github/workflows/ \
  turbo.json lefthook.yml

# Cut 1: incremental state is ignored, so CI can never warm it
grep -n "stryker-incremental" .gitignore

# Cut 4: eve carries no retry in any tier config (expect no output)
grep -n retry ~/Code/eve/packages/eve/vitest.{unit,integration,scenario}.config.ts

# Cut 3: the three populations
grep -rln describeWithPg packages --include='*.integration.test.ts'
```

After Cut 3, the property to hold is that **no test changed tier by accident**:
the file count per tier before and after must account for all 17, and
`pnpm test:pg` must still select exactly the seven `describeWithPg` suites. After
Cut 4, run the integration tier three times on a clean tree — the point of
removing a retry is to learn whether anything is actually flaky, so a green run
is a finding to record, not a formality.
