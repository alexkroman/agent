# Delete the surface pins the epochs and the report already hold

This repo pins its published surface **three** ways, added at three different
times: runtime snapshot tests (`exports.test.ts` in two packages), a committed
static report (`etc/*.api.md` + `API-EXPORTS.json`, gated by
`check:api-report`), and hashed capability epochs
(`contracts/epochs/<capability>/v<N>.json`, gated by `check:api-contracts`).
The third arrived last and is the strongest, and nothing went back to look at
what the first two were still for.

Measured, not assumed. Every runtime export name in every committed export
snapshot, against `API-EXPORTS.json`:

```text
COVER @alexkroman1/aai/llm          runtime=33  api=56
```

17 of 17, zero gaps. The 47 root names are also all inside the 299-name union
of the current `aai` capability epochs. So the snapshots pin a strict subset of
what two merge gates already pin, from a narrower vantage point — runtime keys
only, no types.

This plan removes four things. It removes no gate: each cut is a *second* copy
of a check, or a copy pointed the wrong way, or data no test reads. **The
argument for each is that a duplicate pin is worse than no pin**, because the
weaker of two copies is the one that gets updated when they disagree, and
because a test whose whole content is "the surface is what it was" trains
everyone to reach for `-u`.

## Cut 1 — the snapshot half of `exports.test.ts`, both packages

Delete the `toMatchSnapshot()` assertion at `packages/aai/sdk/exports.test.ts:52`
and `packages/aai-ui/exports.test.ts:21`, and delete both `.snap` files.

**Keep the file, the `SUBPATH_IMPORTS` table, and the loaders.** Two things in
there are not duplicated anywhere and the measurement above says nothing about
either:

- **The `_`-prefix rule** (`exports.test.ts:60`, `aai-ui/exports.test.ts:24`). It
  is a RULE, and `check:api-report` is a STALENESS GATE — it fails when the
  committed file disagrees with the tree, and says nothing about content. Checked:
  `API-EXPORTS.json` carries no underscore name today, and it would silently
  *record* one the first time somebody committed it. That test is the only thing
  standing between the repo and a second `_internals` leak, which is the incident
  the rule was written for.
- **The cold import itself.** Each case loads a whole subpath barrel, so a
  circular import that leaves a name `undefined` at load time fails here. A
  report derived from `dist/*.d.ts` cannot see that at all. This is why the cut
  is the assertion and not the file.

One tradeoff to state rather than hide: the snapshots fail in the unit tier,
which resolves `@alexkroman1/aai` to `.ts` source through `@dev/source` and
needs no build. `check:api-report` reads reports generated from built
declarations, so after this change an export addition is caught *later in the
pipeline*. It is still caught before merge — `check:api-report` is in both
`scripts/check.sh` and the CI check job — and it is caught with better
information, since the report shows the signature and the epoch classifies the
break. Trading "fails 40 seconds earlier" for "fails with the reason" is the
right direction.

While in the file: its header comment ("These tests catch accidental export
additions or removals") describes the half being removed and has to be rewritten
to say what the file is for afterwards. The inline comment at `:20` also claims
the table covers "all ten" subpaths against 15 loaders — already stale, fix it
in the same edit.

## Cut 2 — `schema-shapes.test.ts` snapshots one union twice

`protocol.ts:153` is a literal alias:

```ts
export const ServerMessageSchema = SessionEventSchema;
```

and `schema-shapes.test.ts` snapshots both sides of it — `:35`
(`SessionEventSchema option shapes`) and `:39` (`ServerMessageSchema option
shapes`). Same object, two snapshots, identical by construction. Delete the
`ServerMessageSchema` case and regenerate the `.snap`.

Keep `ClientMessageSchema` (`:43`). It is also an alias — of
`SessionCommandSchema`, at `protocol.ts:165` — but it is the only case covering
the command union, so deleting it would remove coverage rather than a duplicate.
Rename it to `SessionCommandSchema` so the file names the schemas that actually
exist and the aliases stop looking load-bearing.

## Cut 3 — the protocol constants pinned twice, with the weaker copy live

| Constant | `protocol-snapshot.test.ts` | `protocol-compat.test.ts` |
| --- | --- | --- |
| `DEFAULT_STT_SAMPLE_RATE` | inline snapshot `16000` (`:36`) | `=== fixture` |
| `DEFAULT_TTS_SAMPLE_RATE` | inline snapshot `24000` (`:36`) | `=== fixture` |
| `SessionErrorCodeSchema.options` | **exact** inline snapshot (`:45`) | **superset** check |
| `TOOL_EXECUTION_TIMEOUT_MS` | inline snapshot `30000` (`:41`) | — |
| `MAX_TOOL_RESULT_CHARS` | — | `=== fixture` |

Delete `test("sample rates")` and `test("error codes")` from
`protocol-snapshot.test.ts`; keep `test("timeout constants")`, which is the one
constant the fixture does not carry.

The error-codes pair is the reason this cut is worth making rather than merely
tidy: **the two copies point in opposite directions.** The fixture asserts the
current options are a SUPERSET of the pinned list, which is the correct
direction — adding a code is safe, removing one breaks a deployed client. The
inline snapshot asserts exact equality, so it fails when somebody legitimately
adds a code, and it absorbs a *removal* the moment anyone runs `-u`. That is a
gate that fires on the safe change and yields on the dangerous one. Leaving both
means the next person to see red picks whichever is quicker to silence.

Note the surviving copy lives in `protocol-compat.test.ts`, which is red right
now — see "Blocked on" below. This cut lands after that, not before, or it
deletes a working check in favour of a failing one.

## Cut 4 — `packages/aai-server/compat-fixtures/` is read by nothing

`README.md` + `v1.json`, 30-odd pinned `IsolateConfig` and `ToolCallResponse`
payloads, with instructions on the directory ("**Never modify** an existing
fixture file after it's committed", "**Never delete** a fixture unless…"). No
test reads them. The only reader of a directory by that name in the tree is
`packages/aai/sdk/protocol-compat.test.ts:20`, which resolves
`join(import.meta.dirname, "compat-fixtures")` to its own sibling in
`packages/aai/sdk/`.

The provenance is exact: `packages/aai-server/sandbox-compat.test.ts` was
deleted in `30914c9b` ("Guest architecture v2: the sandbox runs the complete
agent"), and its fixtures were left behind. Delete the directory.

Then fix the comment it is cited in. `turbo.json:84` names
`aai-server/compat-fixtures/` as one of three reasons the `test` task needs
`$TURBO_DEFAULT$` inputs — so the repo hashes a fixture set no test reads, and
the comment justifying the hash points at the dead one. The reason itself stays
true (`aai/host/fixtures/`, `aai-ui/fixtures/` and the `__snapshots__` are all
live); only the example goes.

This is the same genre as the `.size-limit.json` that no script referenced and
the `ls-lint` config no pipeline ran, both recorded in `AGENTS.md`. Worth
counting: three now, which is the argument for the deletion being routine rather
than a judgement call.

## What is deliberately NOT cut

- **`protocol-compat.test.ts` and `sdk/compat-fixtures/`.** This is the one tier
  in the repo that asserts a *wire* compatibility claim, and no epoch or report
  can replace it: a capability contract hashes a TYPE surface, and a fixture
  parses a BYTE sequence a deployed peer would send. `/protocol` is in
  `NON_AUTHORING_SUBPATHS`, so the contract mechanism is not even looking at it.
- **The four `.test-d.ts` files.** They are not replaceable by the frozen
  compatibility examples under `contracts/compatibility/`, and the reason
  generalizes: an example can only assert that something COMPILES. A negative or
  a derivation invariant needs `expectTypeOf` — `define.test-d.ts:33` asserts
  `Exclude<keyof AgentDef, keyof Parameters<typeof agent>[0]>` is `never`, and
  `:44` asserts `state` is *absent* from both. No compiling file states either.
- **The epochs vs. the reports.** Both stay, and `AGENTS.md` already gives the
  split (a report answers "what shape", an export list answers "what is in", an
  epoch answers "is this breaking and for whom"). Nothing here disturbs it.

```text
  → PROTOCOL COMPATIBILITY BREAK (v1.json, ServerMessage)
FAIL sdk/schema-shapes.test.ts      3 failed, 1 obsolete
  → obsolete: protocol schema shapes > ClientEventSchema option shapes
```

The event-vocabulary rename in flight for `3-session-event-stream.md` —
`config`→`session.configured`, `audio_done`→`audio.completed`,
`speech_started`→`speech.started`,
`user_transcript`→`user-transcript.committed`, `history` deleted — invalidated
**every message** in `sdk/compat-fixtures/v1.json`. That is the fixture tier
working: it is the only thing in the repo that noticed the rename is a wire

**This plan does not resolve that**, and should not: the decision belongs to the
change that caused it. Per this directory's "A plan here does not design for
backwards compatibility", the shape to expect is a `v2.json` re-baselined on the
new vocabulary with `v1.json` deleted — nothing published depends on the old
spelling, so the fixture README's "never delete" (written for a world with
deployed consumers) does not bind, and it should say so in the same commit
rather than being quietly overridden. Recording the expectation here so 3.1 does
not have to rediscover it.

Sequencing, therefore: **3 lands green, then 3.1.** Cut 3 in particular deletes
a check on the strength of the fixture's, so it cannot precede the fixture being
correct. Cuts 1, 2 and 4 are independent of the protocol work and could land
first if it is convenient; they are grouped here because the reasoning is one
audit, not because the edits interlock.

## What this owes the gates

- **A `.snap` file with no test is an obsolete snapshot, and obsolete FAILS.**
  `update: "none"` is set repo-wide precisely so this is red locally rather than
  only in CI. Deleting an assertion and leaving its `.snap` behind converts a
  cleanup into a broken suite: `packages/aai/sdk/__snapshots__/exports.test.ts.snap`
  and `packages/aai-ui/__snapshots__/exports.test.ts.snap` go entirely (they hold
  nothing else), and `schema-shapes.test.ts.snap` is regenerated with an explicit
  `pnpm vitest -u`.
- **Coverage floors are measured, not reasoned about.** Cut 1 keeps every barrel
  import, so the lines that were executing still execute — but the floors are what
  gates a PR and `pnpm test:coverage` is in `check:local` for that reason. Run it
  per package rather than arguing the deletion is coverage-neutral.
- **No ratchet moves.** Checked all three: none of the touched files appears in
  `escape-hatch-baseline.json`, `guard-invariants-baseline.json`, or
  `file-length-allowlist.json`, so there is no `--update` owed and no headroom
  warning to answer.
- **No capability changes**, so no epoch bump and no `--bump` classification. This
  plan deletes tests and dead data; it adds and removes no export. That is the
  cheap case the README's "adding one is a decision the gate collects" describes
  from the other side.
- **`pnpm changeset add --empty`.** Tests and config only, no release — but the
  pre-push hook wants a changeset for the changed packages either way.
- **`pnpm check:knip`** after Cut 4, per the standing note that a directory
  deletion tends to strand a dependency. Nothing obvious here (the fixtures are
  JSON), which is exactly when it gets skipped.
